# 射影ルール（public-arch-sync profile・記入用テンプレート）

この文書は `/public-arch-sync` が内部正本を公開版 `docs/product/PUBLIC_ARCHITECTURE.md` へ射影するときのルールを定義するプロジェクト固有 profile である。手順・検出フロー・PR 形式・変更なし判定は書かない（正本は `docs/harness/skills/public-arch-sync.md`）。公開区画の構成と公開可否の判定基準そのものも書かない（正本は `docs/CUSTOMER_PUBLISH_POLICY.md`）。

**本ファイルは章構成だけの空テンプレートである。** bootstrap 時に各章の表・パターンを実プロジェクトの内容で埋めるまで、`/public-arch-sync` は判定材料を持たない。未記入のまま実行しないこと。

## 射影の目的（記入前に確認する）

公開版には「変わり得る具体ベンダー名・内部実装構造」を出さず、設計の本質（境界・コンポーネント・
データ配置・処理フロー・セキュリティ）だけを提示する。以下の章は、この目的を機械的に適用可能な
ルールへ落としたものであり、章そのものを削らない（内容が空でも章は残し「該当なし」と書く）。

## 記入手順

1. `docs/product/ARCHITECTURE.md` の見出し一覧を取り出し、§1（削除）と §5（維持）へ**全見出しを
   漏れなく振り分ける**。どちらにも入らない見出しを残さない。
2. `docs/CUSTOMER_PUBLISH_POLICY.md` の公開可否基準を読み、内部限定と判断した見出しを §1 に入れる。
3. 内部正本に出てくる具体ベンダー名・製品名を洗い出して §2 のマッピング表に入れる。
4. §2 の左列のうち**機械的に grep できる語**を §4 の禁止語パターンへ転記する（表示維持と決めた語は
   転記しない。維持理由を §4 に明記する）。
5. §3・§6 をプロジェクトの実態に合わせて調整する。

## 3. 内部構造リーク処理

サービス名の置換だけでは落ちない、構造由来のリークの扱いを定める。

<!-- 記入指示: 以下は汎用の既定。プロジェクトの図・route 構成に合わせて具体化・追加する。 -->

- **prose 中のディレクトリパス表記を出さない**: `apps/*` / `packages/*` 等の内部パス表記は、
  §2 の論理コンポーネント名に置き換える。
- **provider 名を含む route を一般化する**: 外部連携先の名前が入った path は連携先名を落とした
  形にする。公開 API の path は顧客向け情報なのでそのまま残す（一般化するのは連携先名の部分のみ）。
- **内部専用の経路を「使う API」として列挙しない**: 外部イベント受信用・内部定期ジョブ用の経路は
  内部専用と明記し、顧客が呼ぶ API の一覧には入れない。図の中では「（内部）〜」のステップとして
  表現し、実 path を出さない。
- **図の participant alias も禁止語判定の対象**: 図のソースは公開 HTML にテキストとして残るため、
  表示ラベルだけでなく alias 側にも禁止語を使わない。汎用 alias（`DB` / `Store` / `Queue` 等）は
  維持してよい。
- **内部参照 ID を載せない**: 要件 ID・ADR 参照・Issue / PR 番号・内部 docs パスは公開版に出さない
  （§5 の保持要素にも含めない）。
- **同一文書内 anchor リンクを使わない**: 公開ビルド後の見出し ID は安定しないため、相互参照は
  plain text（「後述の〜を参照」）にする。
