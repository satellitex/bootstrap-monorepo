# Refactor Guide Sync — 突合アルゴリズム詳細

> この文書は `refactor-guide-sync.md` の Stage 1〜4 から Read される突合アルゴリズムの正本である。出力先判定・PR 形式は書かない（`refactor-guide-sync-output.md` が正本）。
> 比較基準は常に `origin/main`。

## Stage 1: 正本（coding_guide）インベントリ構築

### 1-1. 全件列挙

```
Glob docs/styles/coding_guide/**/*.md
```

`**` でサブディレクトリ配下も捕捉する。INDEX.md は一覧の起点だが正本ではないため、**INDEX に載っていないファイルも母集団に含める**（INDEX 自体の鮮度ドリフトも観測対象）。`INDEX.md` 自身は規約原則を持たないため突合の母集団から除外してよいが、「INDEX に未掲載のガイドが存在する」ことは追加候補の補助シグナルとして記録する。

### 1-2. 2 モード解析

各ガイドを Read し、構造を実態確認した上で以下のいずれかで解析する。**どのガイドがどちらのモードかは実行のたびに Read で確認して再構築する**（ガイド構成は PJ ごと・改訂ごとに変わるため、固定リストを持たない）。

#### (a) 原則 ID 型

`## 原則` 見出し直後に Markdown テーブル `| <ID> | **<title>** | <desc> |` を持つガイド。各行から `{ID, タイトル, ガイドパス}` を抽出する。

該当ガイドの例示（**placeholder。実行時に Glob + Read して再構築する**）:

| ガイド（placeholder） | ID 体系（placeholder） |
|--------|---------|
| `docs/styles/coding_guide/<pattern-a>.md` | A1, A2, … |
| `docs/styles/coding_guide/<pattern-b>.md` | B1, B2, … |
| `docs/styles/coding_guide/<domain-x>.md` | X1, X2, …（別ガイドと**同字 ID** になりうる — Stage 3 でガイドパスによりスコープ分離） |

抽出時は ID を `{ガイドパス}#{ID}` の複合キーで保持し、同字 ID 衝突に備える。

#### (b) ルール散文型

`## 原則` テーブルを持たないガイド。H2/H3 見出し ＋ 末尾チェックリスト項目（`- [ ]` / `- ` 列挙）を抽出し `{ルール見出し, ガイドパス}` を構築する。これらは体系 ID を持たないため、突合は **ガイドパスの存在チェック**と**見出しテキスト**で行う（ID 完全一致は適用できない）。

該当ガイドの例示（**placeholder。実行時に Read で再確認する**。テンプレート初期状態では `code-comments.md` / `docs.md` / `testing_principles.md` / 言語別ガイドがこの型になりやすい）。

## Stage 2: ガイド側（refactoring_guide）インベントリ構築

`refactoring_guide.md` から 3 系統を抽出する。**検出表ヘッダで 2 構造を分岐**する（ヘッダの実態は Read で確認する）:

1. **デザインパターン検出表**（ヘッダ `| 課題 | 根拠（原則 ID） | 優先度 |`）— 「根拠（原則 ID）」列を抽出。体系 ID と `interface 規約` / `アンチパターン` 等の自由形式が混在しうる。**体系 ID 部分のみを構造化キー**にし、自由形式はその表のセクションヘッダのガイドパスに紐付けて補助照合に使う。
2. **言語規約・共通検出表**（ヘッダ `| 課題 | 検出方法 | 優先度 |`）— 体系 ID を持たない。各セクションヘッダ内のバッククォートリンク `docs/styles/coding_guide/{module}.md` を抽出し、**参照ガイドパス集合**を構築する。
3. **承認済み観点**（`### RG-NNNN: …` エントリ）— 各エントリの「根拠ガイド」フィールドからガイドパス + 原則 ID を抽出する。エントリが 0 件（プレースホルダのコメントのみ）でも正常。

`refactoring_guide.md` が参照する coding_guide パス集合と、Stage 1 で列挙した全ガイドパス集合の差分が、パス単位の追加/削除候補の一次シグナルになる。

## Stage 3: 双方向突合

### 追加検出

```
追加候補 = （規約側 ID/見出し/パス集合） − （ガイド側 参照 ID/パス集合）
```

- 原則 ID 型ガイドの ID で、refactoring_guide の根拠列・承認済み観点のどこにも現れないもの → 観点追加候補。
- Stage 1 で列挙したが refactoring_guide がどの表でも参照していないガイドパス（例: 検出表にセクションが無いガイド）→ ガイド単位の追加候補（「このガイドの観点が refactoring_guide に未反映」）。

### 削除検出

```
削除候補 = （ガイド側 参照 ID/パス） − （規約側インベントリ）
```

- refactoring_guide の根拠列・承認済み観点が参照する原則 ID が、対応するガイドパス内に存在しない → 観点削除候補。
- refactoring_guide のセクションヘッダが参照するガイドパスが Glob 結果に存在しない（ガイドファイル自体が削除/リネームされた）→ 削除候補。

### 誤検出回避（4 規則）

1. **同一性判定**: ID 完全一致を一次キーとする。タイトルのパラフレーズ一致を二次確認に使う。別カテゴリの同字 ID 衝突（別ガイドが同じ接頭字の ID 体系を持つ場合）は、必ず `{ガイドパス}#{ID}` 複合キーで照合しスコープ分離する。
2. **リネーム/更新の除外**: ある ID が規約側に無くても、同一ガイド内に**タイトルがパラフレーズ一致する別 ID**があれば「削除」ではなく「リネーム/更新候補」とし、削除から除外して PR で該当行の原則 ID を旧→新に更新する（行を消さない）。
3. **自由形式根拠**: `interface 規約` / `アンチパターン` 等の ID 化されていない根拠は、体系 ID 突合の対象外とする。これらは**ガイドパスの存在チェックのみ**に留め、ID が無いことを理由に削除候補化しない（誤検出回避）。
4. **散文型ガイド**: ルール散文型ガイドは体系 ID を持たないため、ID ベースの削除検出を適用しない。ガイドパスの存在チェックと、refactoring_guide のセクション有無のみで追加/削除を判定する。

## Stage 4: 振り分け基準

全候補の出力先を **PR** に統一する（Issue 経路は持たない）。編集対象は `refactoring_guide.md` の `## コード課題の検出基準` 配下のカテゴリ表の行のみ。

| 候補種別 | 出力先 | 編集内容 |
|---------|--------|---------|
| 追加候補（規約にあってガイドに無い原則） | PR | 該当カテゴリ表に行を追記。デザインパターン表なら `| 課題 | 根拠（原則 ID） | 優先度 |` 形式で根拠列に当該原則 ID を入れる。言語規約・共通表なら `| 課題 | 検出方法 | 優先度 |` 形式 |
| 削除候補（ガイドに残るが規約から完全消失） | PR | 該当行/セクションを削除 |
| 既存観点の根拠ガイドパス修正（パスのみ陳腐化） | PR | パス文字列の置換 |
| リネーム/更新候補 | PR | 該当行の原則 ID を旧→新に更新（削除＋追加でなく ID 更新） |

> **推論提案の注記**: 追加観点の `課題` 説明・`優先度`（Critical/Must/Should/Nice）・検出方法（grep/lint/手動）は coding_guide に情報が無いため**エージェント推論の提案値**である。これらは **PR レビューが検証ゲート**になる（人間が PR 上で修正・承認する）。PR body にその旨を明記する。

本 Agent は `RG-NNNN` 承認済み観点セクションを生成・編集しない。追記は `## コード課題の検出基準` のカテゴリ表の行に限定する（`RG-NNNN` セクションは Issue → `refactor:approved` → refactorer 承認の別フロー管轄）。
