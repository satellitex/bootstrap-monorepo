# runbook-alignment — 手順書と実装の照合

この文書は `/runbook-alignment` の tool-neutral な正本手順である。手順書の書き方の規約（必須要素・成功判定・状態変更手順）は `docs/runbooks/README.md`、記述の主張と実装を突合する共通手順は `docs/harness/skills/shared/implementation-consistency.md` が正本であり、ここには複製しない。

## 目的

運用手順書（`docs/runbooks/`）に残っている未確定事項と、実装との食い違いを確定させる。質問せずに進め、実装から確定できる事実は確定し、業務判断が要る事項は「未確定」と明記して残し、手順書の本文を修正する。実装は変更しない。差異の評価は、PR 本文の差異評価表に記録する。

## 入力

| 項目         | 必須 | 説明                                                                                                                                                                       | 例                                           |
| ------------ | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 対象の手順書 | No   | 照合する手順書のパス（複数可）。省略時は `docs/runbooks/INDEX.md` から辿れる手順書のうち、未確定・要確認の記述（`TODO`・「未確定」・「要確認」など）を含むものを対象にする | `/runbook-alignment docs/runbooks/<name>.md` |

質問のための確認ゲートは持たない。確認を取りたい事項は、下記「未確定事項の 4 分類」に従って確定または記録する。無人 run での扱いは `docs/harness/skills/shared/unattended-contract.md` に従う。

## 原則

1. 保守的既定が一意に定まる事項だけを、自律で確定する。
2. 定まらない事項は「未確定」と明記して残し、架空の値を書かない。
3. 実装・本番・要件の正本は変更しない。手順書の本文だけを修正する。
4. 本番・共有基盤への操作は、確認のために実行しない。無人であることは、承認が得られたことを意味しない。保守的既定で進めた判断は、PR 本文に未承認の判断として記録し、マージの段階で人間が覆せるようにする（扱いは実行モードによる → `docs/harness/skills/shared/unattended-contract.md`）。

## フロー

### Step 1: 対象と未確定事項の洗い出し

`git fetch origin main` し（`docs/harness/skills/shared/sync-prelude.md`）、対象の手順書を `origin/main` から読む。次を一覧にする。

- 未確定・要確認として残っている記述（責任者・連絡経路・期限・停止条件・SLA・分岐の条件など）
- 実装を名指ししている主張（API・CLI・設定キー・状態遷移・運用操作・数値）

### Step 2: 未確定事項の分類と確定

未確定事項を次の 4 つに分類し、分類ごとに扱う。

| 分類                                                          | 扱い                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 実装から確定できる事実                                        | route・実装・テスト・設定・CI で確認して、本文へ反映する。人に聞かない                                                                                                                                                                                                                               |
| 業務判断が必要な方針（責任者・連絡経路・期限・停止条件・SLA） | 既存 docs・ADR・現行の挙動から確定できれば、それを採る。確定できなければ「未確定」と明記し、必要な枠（責任者・連絡経路・完了条件）だけを残す。架空の期限・担当・SLA を書かない。この判断は PR 本文に、未承認の判断として記録して、止まらずに進める（`docs/styles/team-feedback/autonomous-flow.md`） |
| 既に合意済み                                                  | 無人 run での根拠は、docs・ADR・requirements の記載だけとする。口頭の合意や時間の経過を同意と見なさない                                                                                                                                                                                              |
| 調査しても確認できない事実                                    | 「不明」と書き、不足している証跡と確認方法を添える。推測で確定しない                                                                                                                                                                                                                                 |

確定した内容が、`docs/harness/OPERATING_MODEL.md` の承認モデル節の「人間引き渡し境界」に当たる場合は、その旨を PR 本文の判断の記録に添える。課金と秘密値に関わる事項は、手順書に値を書かず、取得場所と投入手順だけを書く。

### Step 3: 実装との照合

手順書の主張を、`docs/harness/skills/shared/implementation-consistency.md` の §1（主張の抽出）・§2（突合と証拠）・§5（誤検知の回避）に従って実装と突き合わせる。手順書に固有の注意を足す。

- API 例・CLI 例は、入口（route / validator / 引数）→ 処理 → 永続化 → 応答・ログ の順に追う。OpenAPI やコメントだけで判断せず、実際の分岐・返却フィールド・テストと突き合わせる
- 冪等キー・相関 ID・監査 ID などの識別子は、実際の出力で確かめる。出力されない識別子を例に書かない
- 「手順書がそう書いてあるから実装のバグ」「実装がそう動くから要求上正しい」のどちらも、根拠にしない。背景は git log・blame・関連 PR・現行の設計文書で確かめる。PR の説明だけで、解消済みと断定しない

### Step 4: 差異の扱い

差異は、`implementation-consistency.md` の 3 分類（記述修正 / 実装疑い / 判定不能）に割り当てて扱う。

| 差異の種類                                                       | 手順書の編集                                                  | 実装・Issue                                                                                             |
| ---------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 非クリティカルな差異（記述が現行実装と食い違うだけ）             | 現行実装に合わせて本文を書き直す（記述修正）                  | 実装は変更しない                                                                                        |
| 要件・ADR・利用者への契約と、実装が食い違う                      | 本文は書き換えず、差異評価表に記録する（実装疑い / 判定不能） | 実装は変更しない                                                                                        |
| クリティカル候補（データ損失・権限逸脱・重複した不可逆操作など） | 危険な手順を追認せず、本文に中止条件と暫定対応を書く          | 実装の修正は `/create-issue` で別 Issue として追跡する（`docs/styles/team-feedback/scope-boundary.md`） |

- クリティカル候補は、到達可能性・影響範囲・回避手段・証拠の確かさで判定する。用語の差や使いづらさだけでは格上げしない。
- 実装に残る制約は、改修済みであるかのように本文から消さない。制約・回避策・依頼先として手順書に残す。
- 書き直した箇所は、`docs/runbooks/README.md` の必須要素（実施者・権限・事前状態・成功判定・次の操作・再実行可否・証跡）を満たす。

### Step 5: ブランチ → commit → push → PR

編集した手順書がある場合だけ PR を作る。編集がなく所見だけが残る run は、PR を作らず、差異評価表を完了報告に載せる。

`agent/runbook-alignment-YYYY-MM-DD` ブランチ（同日重複は `-2`）を `origin/main` から切り、編集した手順書だけを add し、`docs(runbooks): align <runbook> with implementation` で commit、push する。検証ゲートは `gate:docs`（定義 → `docs/harness/skills/shared/verification-gates.md`）。PR は `docs/harness/skills/shared/pr-creation.md` に従って作る。

PR 本文は標準節（→ `docs/harness/skills/shared/pr-creation.md`「PR 本文の標準節」）に、次を加える。

- 未確定事項の一覧: Step 2 の分類ごとの扱い（確定した事実 / 未確定のまま残した事項 / 不明とした事実）。未承認の判断には、その旨を添える
- 差異評価表: 下記の列構成

## 差異評価表

差異ごとに 1 行で書く。長い証拠は、表の下に行 ID を付けて置く。

| 列             | 書くこと                                                            |
| -------------- | ------------------------------------------------------------------- |
| 指摘・優先度   | 差異の内容と優先度                                                  |
| 根拠           | 手順書・実装・要件の該当箇所。基準にした commit を付ける            |
| 現状と背景     | 確認済み・推定・不明のどれかを明記して書く                          |
| 影響           | 誰が、どの条件で、何に困るか                                        |
| 対応可否・制約 | 実装で直せるか、直せない制約は何か                                  |
| 結論           | 手順書を直した / 実装を別 Issue で追跡 / 両方 / 変更不要 のいずれか |

## 出力

完了後、次を報告する。

- 作成した PR の URL（編集がなければ「PR なし」）
- 確定した事実・未確定のまま残した事項・不明とした事実の件数
- 差異評価表の件数と、別 Issue として起票した件数

## 制約

- 実装・要件の正本・ADR は変更せず、変更が必要な差異は差異評価表と別 Issue に記録する（本 skill の編集範囲を手順書に限るため）
- 確認のための操作は、本番・共有基盤で実行せず、リポジトリ・CI ログ・読み取りの記録で確かめる（無人の run が環境を変えないため）
- 確認できない事実・決められない方針は、「未確定」「不明」と書いて残す（推測や架空の値で埋めると、手順書が誤った操作を促すため）
- 質問で run を止めず、分類表に従って確定または未確定として記録する（応答者がいない run でも結果を出すため）
- `--no-verify` を使わず、hook や検証が失敗したら原因を直す
