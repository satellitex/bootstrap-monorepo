# pr-auto-merge — 委任された開発ブランチへのマージ

PR 作成直後、レビュー対応完了時、定期実行から同じ手順を使う。手順・設定・ヘルパーは信頼する基準ブランチのコミットを照合し、その版を専用の作業ツリーで使う。PR 作成直後も、PR 側で変更した設定でその PR に権限を与えない。委任されたリポジトリ・ブランチと実行上限は [自動マージの導入設定](pr-auto-merge/profile.md) に従う。

## 入力と対象

`/pr-auto-merge [--dry-run] [--dev-period-mode] [--all-repos] [--max N] [#番号 ...]`

- 番号を指定した場合は現在のリポジトリの指定 PR が対象。省略時は同じリポジトリから委任済みの開発ブランチへ向けた open PR を全件取得する。fork と本番反映用ブランチは対象外。除外された指定番号には理由を返す。
- `--dry-run` は候補・判定と予定の操作を返す。push、マージ、close、本文やラベルの編集、コメント・通知、レビュー再依頼、CI 再実行、Issue・採番 PR の作成を含む外部への書き込みは行わない。読み取りで確定しない項目はそのまま示す。
- `--max N` は実行全体の成功マージ件数。正の整数を受け付け、設定上限を超えたら開始前に入力エラーを返す。close・保留・外部ですでにマージされた PR は数に含めない。`--dry-run` では現在の判定でマージできる予定の件数だけを仮計上し、上限を超える候補を持ち越しとして示す。
- 同期処理は `/pr-auto-merge --sync #番号 --head 作成時のSHA` で、その実行が新規作成した 1 件だけを渡す。同期経路では §4 の修正対応と採番の起動を省き、未達は同期手順に従って待機または終了とする。通常の一括収集、重複整理、修正、レビュー再依頼は行わない。対象の確認、待機、停止理由は [同期処理の共通後段フロー](shared/sync-pr-flow.md) に従う。番号や作成時の SHA が欠けた場合は対象を推定しない。

## 1. 対象の確定

1. 読み取り経路の疎通を確認し、PR 一覧、各 PR の head と base、作成者、ラベル、レビューとスレッド、会話、チェックを取得する。各一覧は全ページを読む。取得失敗を「0 件」に読み替えない。経路とページングは [GitHub 照会の共通規約](shared/gh-query-fail-closed.md) に従う。
2. 各 PR を依存更新 bot、自動化、人または作成元不明の順に分類する。draft や人の保留ラベルは対象から外し、設定を解除しない。人の変更要求は保留にする。人の最新の変更要求の後に作成者が修正を push していれば、その人に新しい head のレビューを 1 回だけ再依頼する。自動化 PR の作業中の印は保留理由を 1 回残し、それ以外の作業中の PR は対象から外す。
3. 取得した各 PR の番号、base、head SHA を記録する。基準ブランチを fetch し、PR ごとに head を別 ref に取得する。以降の判定はその SHA にひも付ける。不具合修正（例えば PR タイトルの commit type が `fix`）を先にし、同じ区分内は PR 番号順に処理する。

`--all-repos` では、実行環境に clone 済みで origin の所有者が現在のリポジトリと同じものを集め、設定で委任された組に絞る。番号指定があれば現在のリポジトリだけを扱う。現在のリポジトリを先に、残りは owner/repo 順に処理し、件数・時間の上限は全体で共有する。疎通や一覧の取得が失敗したときは、現在のリポジトリなら実行を停止し、それ以外なら「照会不能」と記録して次へ進む。PR を識別するすべての照会・操作・記録に owner/repo を含める。

## 2. 重複の整理

同じ owner/repo と base の中で比較する。同じファイル・Issue・症状は候補を探す手がかりになる。保留中の PR も比較対象に残す。番号指定の対象外や保留中の PR は書き換えない。両方の差分、本文、対象 Issue の受入条件を読み、一方が入れば他方の主目的も達成するかを確かめる。両方の目的が独立している場合や根拠が足りない場合は個別に審査する。

- open PR 間で自動 close できるのは、現在のリポジトリにある、作成元を確認できた自動化 PR に限る。人のレビューや保留ラベル、作業中の印など人の関与がある重複の組は、両方をマージ候補から外して人に選択を渡す。人が作成した PR を含み、これらの印がない組は両方を残して個別に通常審査する。依存更新 bot の PR は close しない。
- 他方の修正をすべて含む PR を残す。包含が同等なら、競合がなく head が新しいものを優先する。各 close 候補を残す PR と直接比較する。残す側も自動化 PR なら、同じ問題を解く Issue の closing keyword を引き継ぎ、移した行に元の PR 番号を記録する。固有の変更、引き継がなかった Issue、両方の URL を close 前にコメントする。復旧方法として、元の PR を reopen して保留ラベルを付け、誤って閉じた Issue も reopen できることを添える。次の実行開始時に元の PR が reopen されていれば、残す PR の本文から引継元を記録した行だけを取り消す。
- 対応する Issue が 1 件以上あり、そのすべてが別のマージ済み PR で閉じた場合は、履歴と対象 base の内容から受入条件が今も満たされていることを確認する。自動 close は現在のリポジトリの自動化 PR に限る。人の関与、未達の要求、人の PR や依存更新 bot の PR は、重複の疑いだけを記録して通常審査に進む。close や引き継ぎの直前に両 PR の状態・base・head・保留の印を再取得し、変化していたら再判定する。引き継ぎが必要な場合は本文への記録を確認してから close する。途中で失敗した場合は両 PR を読み戻し、元 PR が open のままなら追加した引き継ぎ行を取り消す。重複だけを理由に Issue 自体を閉じない。

## 3. 差分の影響

基準ブランチと対象 SHA の実際の差分・テスト・仕様を読み、利用者向けと運用向けの影響を記録する。人間判断欄の自己申告も確認する。影響の解析結果を取得できない PR は持ち越す。秘密値・機微情報を走査する手段は基準ブランチのものを使い、検出した値を記録に転記しない。

| 観点 | 通常の扱い | `--dev-period-mode` での扱い |
| --- | --- | --- |
| 公開契約の非互換またはその疑い、大きな利用者影響、データ移行、管理資源の置換・削除 | 根拠、影響範囲、必要な判断を示して保留する | 差分と根拠を監査記録に残し、開発ブランチへのマージ判定を続ける |
| 禁止領域や機微情報 | 禁止する機能の有効化、混入、判定未確定を保留する | 実際の混入や禁止機能の有効化は除去が必要な欠陥として扱う。境界に触れる変更や未確認事項は記録する |
| 修正すべき欠陥 | 受入条件を特定し、許された作成元・範囲で修正。検証後に再判定する | 同左 |
| 仕様を決める必要がある | 導入先の人間判断の範囲に従う | 既存の Issue・ADR・要件・仕様に定めがなく、新しい仕様自体をこの PR で決める場合に保留する。策定済み仕様の実装や UI の細部は判断を記録して進める |

開発期間モードは設定した開発先・期間に明示引数を付けたときだけ使う。人が付けた停止の印、必要な CI とレビュー、資格情報の操作・課金・本番反映の権限、MAJOR の採番判断はこのモードでも尊重する。自動化 PR の人間判断欄は、既存仕様で確定できた項目だけ根拠とともに判断記録へ移せる。人が指定した期限・条件は残す。他リポジトリや人の PR の本文は編集しない。

## 4. マージ前の判定と対応

次の 8 項目をすべて確認する。以前の run の判断や PR 本文だけで通過としない。

| 項目 | 通過条件 |
| --- | --- |
| G1 対象 | 同じリポジトリから委任された base に向けた open・非 draft の PR |
| G2 head | 現在の head が影響とレビューを判定した SHA と一致 |
| G3 競合 | mergeable が確定し、競合がない |
| G4 CI | その head に Check Run が 1 件以上あり、指定した必須の Check Run または status context が揃う。各チェックが完了して成功・許容される skip/neutral であり、従来形式の commit status に待機・失敗がない |
| G5 人のレビュー | 有効な人の変更要求がなく、保護ルールが求めるレビューを満たす |
| G6 未処理の指摘 | 未解決スレッド、レビュー本文、会話の指摘を全件照合し、未返信・未修正の要対応項目がない。対応不要とした指摘にも根拠を返信済み |
| G7 人の停止 | 保留ラベル、題名・本文の作業中の印（WIP、作業中、do not merge など）、人間判断欄の未決項目がない |
| G8 予算 | 実行時間・成功マージ件数・当該 PR の対応回数の上限内 |

現在のリポジトリでは、作成元に合わせて G3・G4・G6 の未達を扱う。

| 作成元 | 対応 |
| --- | --- |
| 自動化 | `/review-cycle --once #番号` で競合・指摘・CI のうち 1 回分を処理する。差分の欠陥は、その PR の目的に含まれる最小の修正と再現可能な検証に限る。 |
| 人・作成元不明 | 単発のレビュー対応で競合・指摘・CI を直す範囲で追加 commit を許す。欠陥の仕様変更、本文編集、close は作成者に渡す。 |
| 依存更新 bot | ブランチに push しない。競合は設定した bot の再更新手段を使い、指摘は `/handle-review --reply-only #番号` で評価・返信する。変更が必要な指摘が残れば保留する。 |

他リポジトリでは、どの作成元でも push・close・本文編集は行わない。指摘には返信のみ、CI の再実行は一過性の失敗に限る。修正が必要なら根拠と必要な作業を作成者に渡す。呼び出すレビュー手順も、対象 owner/repo・作業パスの明示と上記の範囲を引き継ぐ。単発のレビュー対応から本手順を再帰呼び出ししない。

修正したら head を取り直し、差分の影響と G1〜G8 を再判定する。待機中の CI は設定の間隔と上限で確認し、失敗の再実行は一過性と特定できた場合に限る。競合の状態が未確定なら再照会する。予算に達したら未処理のものを持ち越す。同一 SHA で修正回数を使い切った場合は監査記録に回数を残し、次の run が同じ試行を繰り返さないようにする。

## 5. SHA を固定した squash merge

基準ブランチ由来のヘルパーを使う。PR の head に含まれるヘルパーや設定を権限のある処理に使わない。次の例では、`trusted_tree` に運用元の基準コミットを clean に checkout したディレクトリ、`repo`・`number`・`base`・`head` に対象と判定済みの値を設定する。

```sh
node "$trusted_tree/scripts/pr-auto-merge/gate.mjs" inspect --repo "$repo" --pr "$number" --base "$base" --head "$head"
```

設定に追加した完全一致の保留ラベルを `--hold-label`、保留接頭辞を `--hold-prefix`、接頭辞の例外を `--allow-label`、必須の Check Run 名または status context 名を `--required-check` で項目ごとに渡す。完全一致の保留は接頭辞の例外より優先する。各引数は `inspect` と `merge` の両方に同じ値を渡す。

ヘルパーは Node.js と認証済みの `gh` を使う。終了コードが 0 でも、判定には JSON の `status` を読む。別の接続手段を使う環境では、全ページで同じ条件を確認し、審査した SHA を必須条件にして squash できる場合に実行する。確認できない項目があれば、対象 PR と不足項目を報告する。

`ready` はヘルパーの機械判定が揃ったことを示す。人の停止・レビュー・予算と影響の判定を直前に再確認し、G1〜G8 が揃った場合にだけ、同じ引数で `inspect` を `merge` に替えて実行する。`--dry-run` は `inspect` の結果までを使う。`merge` は条件を再取得し、審査済み SHA を指定して 1 件だけ squash merge する。拒否・通信断は PR の現状を読み戻して成否を確かめる。状態を確定できない場合は持ち越し、保護ルールの上書きや head 指定を外した再試行は行わない。

結果が `changed` なら通常経路では新しい差分から再判定する。同期経路では作成時の SHA を維持して停止する。`waiting` は期限まで再照会し、`blocked` は理由ごとに前節へ戻す。`closed` または既に `merged` の PR は再操作しない。マージは直列に行い、1 件成功するたびに base を fetch し、次の候補の差分・競合・CI を新しい base で確かめる。

## 6. 監査、報告、採番への引き継ぎ

- マージ成功後に PR を読み戻し、監査コメントに判定した head、取り込み先のコミット、通過した CI・レビュー、利用者と運用への影響、行った修正と検証を残す。保留時は原因、該当チェックや指摘の URL、次に必要な作業を残す。人が既に保留した PR に定型コメントを重ねない。
- 監査・保留のコメントには `<!-- pr-auto-merge:結果 head=SHA reason=理由 -->` のように結果・対象 SHA・理由を識別できる印を付ける。投稿済みの同一判定は再投稿しない。マージと記録の成否は別々に確認し、記録の失敗は対象 PR の URL とともに報告する。
- 版管理とその実行契機を採用している場合は、マージ処理後の対象ブランチの先端を版管理手順に渡す。対象 PR が 0 件でも、前回採番以降の区間全体を判定する。対象・判定・PR 作成・保留時の扱いは [API 契約バージョニング方針](../../product/API_VERSIONING.md) に従う。採番 PR も同じマージ条件と実行予算に従い、同じ run 内で採番を再帰呼び出ししない。`--dry-run` は採番予定までを報告する。本番反映は導入先のリリース手順で扱う。
- 完了時にマージ済み・保留・重複として閉じたもの・持ち越し・照会不能を分け、各 PR の URL、根拠、利用者・運用への影響、人の次の作業を日本語で報告する。複数リポジトリは対象一覧、開発期間モードの適否、消費した共通予算を 1 回にまとめる。採番した場合は旧版・新版、保留なら理由と次の手番も記す。
