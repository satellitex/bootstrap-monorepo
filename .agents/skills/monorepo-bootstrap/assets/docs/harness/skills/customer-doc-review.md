# customer-doc-review — 対外ドキュメントの多視点レビュー（opt-in:public-site）

この文書は `/customer-doc-review` の tool-neutral な正本手順であり、レビュー観点・レポート構成も本文に収録する。**opt-in:public-site グループの資産**であり、対外公開区画を持たない PJ では収録しない。公開可否の判定基準・機械検査の正本は `docs/CUSTOMER_PUBLISH_POLICY.md` に置き、ここには書かない。

## 目的

社外・顧客・管理組織へ共有される対外ドキュメント（公開サイト生成物・`docs/customer/` 配下の資料等）を、複数の固定観点で並列レビューし、誤検知を除いた改善提案を 1 つの統合レポート（観点別の表）にまとめる。任意で指摘を issue 化する。

対象読者の立場（顧客 / 開発側開発者 / 開発側ビジネス）に加え、対外文書特有のリスク（情報漏洩・情報設計・対外表現コンプラ・用語整合）を専門観点として常設する。

## いつ使うか

- 対外/共有ドキュメントを公開・更新する前後の品質ゲートとして
- 「この共有ドキュメントをレビューして」と指示されたとき
- 公開用サニタイズ・公開ゲートの取りこぼし監査として

コードの diff レビューは対象外（→ `/code-review` 等）。本 skill は**散文・表・生成 HTML の文面**を見る。

## 入力

| 項目 | 必須 | 説明 |
|------|------|------|
| ターゲット | Yes | 公開区画の slug または任意の共有ドキュメントのパス |
| 観点の追加/除外 | No | 既定 7 観点（下記）に対する増減。未指定なら全観点 |
| issue 化 | No | 指摘を issue 化するか。未指定なら統合レポート出力のみ |

ターゲットが曖昧なら、PJ の公開区画一覧（生成スクリプト・`docs/customer/README.md`）から候補を提示して確認する。

## フロー

親 session がオーケストレータ（subagent は read-only 分析のみ）。

### Step 1: ターゲット準備（顧客が実際に見る文面の確定）

レビュアーが「顧客が実際に目にする文面」を見るための前処理。手順の骨格は次の 2 点（具体のビルドコマンド・抽出レシピは PJ の生成パイプラインに合わせて bootstrap 時に具体化する）:

1. **顧客可視テキストの確定**: 対象が生成物ならビルドし、顧客が実際に見る公開ファイル集合を確定して、読み下しテキストへ展開する（HTML はタグを除き見出し・表・リスト構造を保持）。巨大な明細は全文（grep 用）と横断サンプル（精読用）の 2 ファイルに分ける。
2. **サニタイズ文脈の採取**: そのパイプラインのサニタイズ処理（除去・置換パターン）と公開ゲート（機械検査）を読み、「既にフィルタ済みのもの」と「素通しするもの」を一覧化したメモを作る。レビュアーが既処理済みを誤指摘しないために必須であり、「素通し」の一覧が今回見つけるべき本丸を定義する。

成果物（本文ソース・レンダリング済み全文・横断サンプル・サニタイズ文脈メモ・裏取り用の数値サマリ）は scratchpad に置く。

### Step 2: レビュアー編成

既定は 7 観点。各観点のレンズは下記「観点カタログ」を正本とする。ターゲットの性質に応じて観点を増減してよい（例: API 仕様書なら「破壊的変更・後方互換の明示」観点を追加）。追加した観点と狙いは最終レポートに明記する。

### Step 3: レビュー（並列・read-only）

各観点を**独立した read-only subagent** として並列に spawn する。各 subagent には以下を渡す:

- 役割と観点のサブ基準（観点カタログの当該レンズ）
- Step 1 の成果物パス（精読は横断サンプル、件数確認は grep で全文、と指示する）
- **用語許容方針**（下記）と「既にフィルタ済みのものは指摘しない」原則

各 subagent は観点ごとに**実物の文言引用付き**の指摘（見出し / サブ基準 / 該当箇所 / 問題 / 深刻度〔高・中・低〕/ 具体的改善案）を構造化して返す。指摘は深刻度の高いものを優先し厳選する。

### Step 4: 検証（誤検知除去）

各観点の指摘を、当事者とは独立に実コンテンツへ突き合わせて検証する:

- 引用文言が実在するか確認し、該当箇所を実物に合わせる
- **既にサニタイズ済みのもの**を誤って漏洩指摘していないか → 却下
- **用語許容方針**に反する過剰指摘（公開仕様の標準語を不当に問題視）→ 却下
- 改善案が具体的・実行可能か。各指摘に確信度（確実/推定）と判定（維持/修正/却下）を付す

却下した指摘は理由付きで残す（統合時に重複・誤検知の学習に使う）。

### Step 5: 統合・出力

検証済み指摘を 1 レポートに統合し、**チャットの最終応答として直接出す**（ファイル化はユーザー指示時のみ）。構成（この順）:

1. **総括（5〜8 文）** — 到達点を公平に（良い点も加点する）+ 最重要の構造的問題 1〜2 点 + 公開の前提条件
2. **横断トップ課題** — 重複を束ねた優先度付き表 `| 優先度 | 課題 | 影響（効く観点） | 推奨アクション |`（P0/P1/P2、上位 5〜7 件）
3. **観点別 改善提案表** — 観点ごとに `| 深刻度 | 指摘（該当箇所付き） | 改善案 |`。ユーザー指定の観点を先、追加観点を後に並べ、追加観点には「追加理由」を 1 文添える。改善案は可能な箇所を **Before→After の文言例**で示す
4. **追加で立てたレビュアーと狙い**
5. **実装の打ち手（優先順）** — 機械的フィルタ拡張（短期・低コスト）／構造変更（中コスト）／文面の正本化（高コスト・最高効果）の段構えで、生成パイプラインのどこを触るかを具体パスで示す

統合の原則: 重複は束ねる / 深刻度は影響（顧客が読めない・機密漏れ・誤認リスク > 表記ゆれ）で再評価 / 抽象論でなく Before→After で示す。レポート末尾に裏取りに使った実値（grep 件数・集計）を 1〜2 行添える。

### Step 6（任意）: issue 化と milestone 割当

issue 化を指示された場合、**1 指摘 = 1 issue にせず打ち手（実装単位）でグルーピング**する（同じファイル/機構を触る指摘は 1 issue に束ねる。文面微修正の小粒指摘は観点横断で 1 issue に集約。目安 8〜12 issue、各 issue は単独着手可能な粒度）。Issue 本体の作成・Project・Status・Expired date は `/create-issue`（`docs/harness/skills/create-issue.md`）の規約に委譲し、campaign 用 milestone を作成または既存の妥当な milestone を使って全 issue を割り当てる。受入条件には可能なら「Before→After の文言例」「機械検証の追加」を含める。

## 観点カタログ（既定 7 観点）

全レビュアーに共通で用語許容方針と Step 1 のサニタイズ文脈メモを渡し、「散文部と明細部（生成データ由来の表など）は品質水準が異なりうるため、どちらの話かを明示する」よう指示する。

1. **顧客視点** — 対象読者（内部実装に非専門）として: 意味不明な文言（内部シンボル・身内の作業語の混入）/ 導線・探索性 / 読みやすい project language / 簡潔さ / やったこと・やることの区別が伝わるか
2. **開発者視点（正確性・誠実性）** — 自社が顧客に出す文書として: 数値・状態表記が実体と整合するか / できないことを書いていないか（未実施を実施済みに見せる表現）/ 身内向け用語 / 秘匿情報・攻撃面ヒント
3. **ビジネス視点** — 事業責任者/プリセールスとして: オーバープロミス・誤解を招く保証表現 / 非エンジニアの意思決定者に価値が伝わるか / 購買・信頼判断へのマイナス要因
4. **情報漏洩・秘匿性監査** — 内部実装詳細（内部変数名・カスタムエラー名・内部識別子）が攻撃者/競合に与えるヒント / 機密の素通し（commit ハッシュ・secret 名・dev ホスト名・防御内部設計）/ 容量・需要数値等の事業機密。grep で残存語と件数を数えて根拠を示す
5. **情報設計・ドキュメント UX** — 大量明細の探索可能性（絞り込み・サマリ層）/ 情報密度の落差・中間抽象度の欠落 / 数値の母数対応 / モバイル・印刷での見え方。構造改善を具体的に提案する
6. **対外表現・コンプライアンス** — 断定表現（「担保済」等）が実体に対しオーバークレームにならないか / headline 数値の一人歩き / 未確定（TBD・目標値）の誤読 / 契約・SLA・監査で引用されたときの係争耐性。誠実で防御可能な表現案を提示する
7. **一貫性・用語整合** — 表記ゆれ / 呼称が用語正本（`docs/product/TERMS.md`）と一致するか / 数値の内部整合（内訳の合算・割合の根拠）/ 見出し・ラベルの粒度と命名の一貫性。grep で実件数を示す

## 用語許容方針（重要）

**公開情報で使われる標準語は、過度に分かりにくくなければそのまま使ってよい。** 問題は「内部実装シンボル」と「身内の作業語」。

| 区分 | 例 | 扱い |
|------|-----|------|
| 公開仕様・標準語（許容） | 公開規格・公式ドキュメントに載る用語（HTTP ステータスコード、OAuth、REST 等）とドメインの公知用語 | 過度に難解でなければ可。無理に言い換えない |
| 内部実装シンボル（不可） | 内部変数名 / カスタムエラー名 / イベント名 / 関数シグネチャの内部引数 / 内部 ID | 業務語へ言い換え or 非表示 |
| 機密（不可） | commit ハッシュ / secret・binding 名 / ライブキー接頭辞 / dev ホスト名 / PR 番号 / 内部行番号 | 除去（サニタイズ + ゲートで二重防止） |
| 身内の作業語（不可） | テスト工学語の生出力（assert/describe 等）/ 内部工程語 / 作業メモ | 除去 or 業務語へ正規化 |

判断基準: 「公開仕様書・標準規格にその語が載っているか」「非専門の対象読者が文脈で意味を取れるか」。両方 Yes なら許容、どちらか No なら言い換え/除去。

## 制約

- subagent は **read-only**（Read/Grep/Glob/Bash の検査用途のみ）。ドキュメント本体やコードを編集しない（改善は issue/PR で別途）
- 指摘は必ず**実物の文言引用**を伴う。抽象論・憶測のみの指摘は出さない
- レビュー対象は文面。コード品質・diff は対象外
