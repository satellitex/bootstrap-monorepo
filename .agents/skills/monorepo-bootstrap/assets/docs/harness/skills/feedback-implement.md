# feedback-implement — 承認済み Issue の実装と進捗の返信

[受付の profile](../../../.claude/skills/feedback-triage/references/chat-profile.md) の対象ラベル・上限を使い、[チャットの共通契約](shared/chat-feedback.md) の実行枠で起動する。`/feedback-implement --dry-run` は候補の選定・突合と予定の報告だけを行う。

## 実装対象を選ぶ

1. [gh 照会の共通規約](shared/gh-query-fail-closed.md) に従い、Issue、ラベル、対応する PR をページ末尾まで読む。open Issue のうち、出所ラベルと自動実装ラベルの両方が付いており、本文の印が登録済みの受付を指すものを対象にする。出所・受付・担当 bot の起票記録を照合し、自動実装に同意された受入条件と Issue を突き合わせる。内容や対象が変更されていれば triage に戻す。
2. 本文または PR の関連付けから、すでに当該 Issue を閉じる PR が開いているものを取り除き、既存 PR を進捗報告に使う。着手ラベルがあるときは、その Issue を扱う run が終了済みであることを実行履歴で確認する。確認できなければ着手中として保留する。途中終了済みなら既存 PR・作業ブランチを確認し、その作業を引き継ぐ。引き継げない場合は理由を残し、自動実装から外して再開条件を報告する。
3. 残った候補から、依存関係を満たすものを優先度順、同順位なら古い順に、profile の上限まで選ぶ。競合して同時実装できないものは次の run に残す。処理直前に open 状態、内容、ラベル、対応 PR を読み直し、変化がなければ着手ラベルを付けて読み戻す。

## PR を作る

選んだ Issue 番号を渡し、[multi-issue](multi-issue.md) の計画・実装・検証・レビュー・PR 作成を行う。課金・秘密値など、実装中に判明した人間への引き渡し境界は [承認モデル](../OPERATING_MODEL.md) に従う。起票案の ✅ はそこで示した Issue と実装対象の確認である。PR のマージ、本番配備の権限はそれぞれ導入先の既存手順と明示的な委任に従う。

| GitHub で確認した結果  | Issue と元スレッドへの操作                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| PR を open             | PR との関係を確認し、`[PR作成 n]` で URL を返す。次の run は既存 PR を使う                     |
| PR をマージ            | 既定ブランチへのマージと対応 Issue を照合し、`[マージ済み n]` で URL を返す                    |
| 未着手のまま次回へ延期 | 自動実装の対象を維持する。着手ラベルだけを外す                                                 |
| 実装を継続できない     | 理由、既存 PR、再開条件を Issue にコメントする。自動実装ラベルを外して `[実装見送り n]` を返す |

着手した各 Issue は、結果を GitHub に記録してから着手ラベルを外す。返信は、その Issue の本文とコメントにある各項目の印を照合し、元のスレッドに届ける。別受付の資格情報が現在の run にない場合や送信が失敗した場合も GitHub の結果を保ち、[feedback-triage](feedback-triage.md) が各受付で不足した返信を補う。

対象 Issue、PR、延期・見送りと理由、送信済み・未送信の返信先を完了報告に残す。対象があった run は運用担当へ [情報通知](shared/notification-contract.md) を送る。本番反映は導入先のリリース手順（`/deploy-verify` 採用先ではその本番用手順）で行い、triage がその結果を元スレッドに返す。
