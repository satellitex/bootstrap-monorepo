# 無人 run の共通契約

この文書は、人間が同席しない run（scheduler 等から起動される無人 run）で、手順が持つ確認ゲートをどう扱うかの正本である。各手順の本文、承認モデルの定義（`docs/harness/OPERATING_MODEL.md`）、routine の登録手順（`docs/harness/scheduled-operations.md`）はここに書かない。

## 適用条件

起動プロンプトの冒頭 1 行で次を書き、この文書を読ませた run を「無人 run」とする。読ませていない run は人間が同席する対話 run であり、各手順の確認・承認はそのまま実行する（対話 run の挙動は変えない）。

```text
docs/harness/skills/shared/unattended-contract.md を読み、無人 run として以降の手順を実行する。
```

判定を run 側の宣言に置き、確認ゲートの側が実行モードを見る形にするのは、「確認を取る」と「確認を待たない」という矛盾した指示が同じ文脈に同居すると run ごとに挙動が揺れるためである。呼び出し先へ無人フラグを書き回す方式では、書き漏らした箇所が対話前提のまま残る。

確認ゲートを持つ手順は、ゲートの箇所に「扱いは実行モードによる（→ `docs/harness/skills/shared/unattended-contract.md`）」と書き、無人 run での既定動作を 1 文で添える。

## 3 つの条件を混ぜない

無人 run で成り立つのは 1 番目だけである。承認を省くことと承認されたことは別であり、検証に失敗した run は失敗として報告して終える。

| 条件                     | 無人 run での真偽    |
| ------------------------ | -------------------- |
| 人間に質問できない       | 真。質問の手段がない |
| 人間の承認が得られている | 偽                   |
| 成功するまで進んでよい   | 偽                   |

## 対話待ちになるもの

無人 run には応答者がいないため、次は呼ばずに代替経路へ進む（呼ぶと、run が応答待ちのまま再開されないことがある）。

- 質問ツールなど、人間への問い合わせを要求する tool 呼び出し
- 承認プロンプトを伴う tool 呼び出し（scheduler が許可していない tool を含む）
- 端末の入力待ちを伴うコマンド（device code 認証、対話インストーラ等）
- 認証・認可の更新待ち（不足した scope の付与を人間に依頼する経路）
- 資格情報を持たない外部システムへの接続。接続を試みず、同じ事実を登録済みの読み取り専用 API・リポジトリ・CI ログで確かめ、確かめられない事実だけを「未確認（資格情報なし）」と報告する

## 確認ゲートの扱い

| 遭遇する指示                                                                                                  | 無人 run での扱い                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 解決策の選択肢の確認（「A / B から選ぶ」「要否を判断する」）                                                  | 確認を取らず 1 案に決める。根拠は既存 docs → 一次情報 → 業界標準 → 保守的 default の順に探し（`docs/styles/team-feedback/autonomous-flow.md`）、選んだ案と理由を成果物に確定事項として書く（解決策の確定 → `docs/styles/team-feedback/single-solution.md`）。人間へ渡すのは、選んだ案が承認必須 2 種（課金・秘密値）に該当する場合と、導入先が `docs/harness/OPERATING_MODEL.md` の「人間引き渡し境界」に定めた区分に該当する場合だけ |
| 人間しか知らない事実を聞く                                                                                    | リポジトリ・CI ログ・読み取り専用 API で確かめる。確かめられない事実は現状の仕様を変えない前提で進め、「未確認の前提」として成果物に明記する。作業を止めるのは、その事実に依存する作業が承認必須 2 種に当たる場合だけで、依存しない作業は続ける                                                                                                                                                                                       |
| 生成物の内容確認（起票内容・本文・実行計画の提示）                                                            | 提示内容を完了報告に含め、確認を待たずに続行する                                                                                                                                                                                                                                                                                                                                                                                      |
| 元に戻しにくい操作、または手順が人間に残している操作の承認（マージ、prod への反映、秘密値の操作、データ削除） | 操作を行わず、実施する場合の内容・根拠・影響を 1 案として成果物に残して人間へ渡す                                                                                                                                                                                                                                                                                                                                                     |
| 権限・認可の更新を人間に依頼する                                                                              | 依頼せず、当該処理をスキップして「未実施」と理由を報告する                                                                                                                                                                                                                                                                                                                                                                            |
| 必須情報が揃わない                                                                                            | 推測で埋めず、当該処理を行わずに不足項目を明示して呼び出し元へ返す。任意項目の既定値は、手順が定めるとおりに補ってよい                                                                                                                                                                                                                                                                                                                |
| 検証（読み戻し・往復検証・検証ゲート）が失敗した                                                              | 成功と報告しない。ERROR / WARN の強度は各手順の規定のまま維持する                                                                                                                                                                                                                                                                                                                                                                     |

## 変えないもの

- 操作の許可範囲。無人であることは、各手順が人間に残している操作を実行してよい根拠にならない
- 承認必須 2 種（課金・秘密値）は人間が行う
- 検証の必須性と失敗時の強度
- 成果物の構成と報告項目。無人 run では報告が人間の唯一の確認材料になるため、省略しない

## 実行基盤との関係

本文は実行基盤に依存しない。対話待ちになる呼び出しを呼ばずに代替経路へ進めば、基盤による停止の有無によらず同じ結果になる。基盤固有の事実は、`docs/harness/OPERATING_MODEL.md` の「ツール固有手段の読み替え」と、routine 登録時のチェックリスト（`docs/harness/scheduled-operations.md`）に置く。
