# 実装整合の共通手順（記述の主張と実装の突合）

この文書は、sync 系 skill が共通で実行する「記述の主張を実装で確かめ、矛盾を 3 分類に割り当て、分類に応じて編集または記録する」手順と、PR 本文での記録形式の正本である。何が矛盾か、どちらを正とみなすかの規約は `docs/styles/coding_guide/docs.md` の「実装整合の原則」節が正本であり、走査対象のファイル集合は各 skill 文書が持つ。この 2 つはここに複製しない。

呼び出し側の skill 文書は、該当する Step で本ファイルを Read し、その手順に従う。

## 1. アンカー付き主張を抽出する

アンカー付き主張とは、実装側の実体（アンカー）を名指ししているため、実装を読めば真偽が判定できる記述である。アンカーを持たない散文（目的・背景・設計意図）は対象外とする。真偽を機械的に決められず、書き換えが推測になるためである。

| アンカー種別                                   | 記述側の例                                   | 実装側の引き当て                                                |
| ---------------------------------------------- | -------------------------------------------- | --------------------------------------------------------------- |
| ファイル・ディレクトリのパス                   | 「生成スクリプト（scripts 配下）が生成する」 | `git ls-tree -r --name-only origin/main` で実在を確認する       |
| 関数・型・エクスポート名                       | 「`verifySignature` が署名を検証する」       | `git grep -n '<識別子>' origin/main -- <実装のパス>`            |
| HTTP ルート・エンドポイント                    | 「`POST /api/v1/items`」                     | ルート定義を `git grep` し、method と path を読む               |
| 環境変数・設定キー                             | 「`SERVICE_API_URL` を参照する」             | 参照箇所と定義箇所（設定スキーマ・env 例）を読む                |
| 数値パラメータ（間隔・上限・TTL・retry・閾値） | 「毎時 1 回」「上限 10 req/min」             | cron 式・定数・設定値の定義箇所を読む                           |
| 状態・ロール・イベント名                       | 「`admin` ロール」                           | enum・定数・型の定義を読む                                      |
| 実行コマンド（script / task / CLI）            | 「`./scripts/seed.sh` を実行する」           | `package.json` の scripts、task runner の定義、CLI の実体を読む |

IaC や宣言ファイルを持つ導入先は、リソース名・モジュール名の行を追加してよい。

## 2. 突合して証拠を残す

主張ごとに、実装側の実体を `origin/main` で読み、一致か不一致かを判定する。不一致には、実装側の根拠（パスと識別子、必要なら行番号）を必ず添える。根拠を示せない不一致は検出にしない。証拠のない「おそらく古い」は推測であり、記述を推測で書き換えると、正しい記述を壊す。

## 3. 3 分類に割り当てる

矛盾は「記述修正」「実装疑い」「判定不能」のいずれかに割り当てる。分類の定義、層ごとの既定、「判定不能」で正とする側を決める方法は `docs/styles/coding_guide/docs.md` の「矛盾の分類」節に従う。この文書では、分類から操作への対応だけを定める。

| 分類     | 記述側の編集                                                            | 記録先                                                    |
| -------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| 記述修正 | する（`docs/styles/coding_guide/docs.md` の「修正の作法」の範囲に限る） | PR 本文の修正一覧（呼び出し側の Report 形式）             |
| 実装疑い | しない                                                                  | PR 本文の「実装側判断要」区分                             |
| 判定不能 | しない                                                                  | PR 本文の「実装側判断要」区分（正とする側と理由を添える） |

- 呼び出し側の編集可能スコープ外にあるファイルは、分類が記述修正でも編集せず、「実装側判断要」区分に記録する。
- この手順は Issue を起票しない。実装側の判断が要る所見は、PR 本文の記録で人間に渡す。人間は PR のレビューで判断を覆せる。

## 4. 「実装側判断要」区分の記録形式

PR 本文に「実装側判断要」区分を置き、実装疑いと判定不能を 1 件 1 行で列挙する。

| 分類                | 記述側（ファイル・箇所・主張の引用） | 実装側の根拠（パス・識別子・行） | 規範の出典                                 | 正とする側と理由               | 実装側で必要な変更       |
| ------------------- | ------------------------------------ | -------------------------------- | ------------------------------------------ | ------------------------------ | ------------------------ |
| 実装疑い / 判定不能 |                                      |                                  | 実装疑いのとき、規範の記述のパスと該当箇所 | 判定不能のとき、決めた側と理由 | 例: 実装を記述に合わせる |

- 該当がない run は、区分ごと省かず「なし」と書く。
- 編集（記述修正と、呼び出し側が定める他の自動編集）を 1 件も含まない run は PR を作らない。この場合の記録先は完了報告であり、同じ表を完了報告に載せる（→ `docs/harness/skills/shared/sync-prelude.md` の「編集を伴わない所見だけの run」）。

## 5. 誤検知を避ける

1. **抽象度の差は矛盾ではない**: 記述が実装を要約しているだけの場合（「署名を検証する」に対して実装が 3 種の検証を持つ）
2. **例示コード・サンプル値**: コードフェンス内の例示と、`example.com` などのプレースホルダ
3. **将来・課題マーカー**: `TODO:` / `FIXME:` / `NOTE:` / `HACK:` を付けた記述は、現状の主張ではない
4. **環境差**: 環境ごとに値が異なるとき、記述がどの環境を述べているかを確認してから判定する
5. **意図的な凍結**: 呼び出し側が走査対象から外したアーカイブ（採用判断時点の snapshot 等）は、乖離が正常である
6. **重複した検出の抑止**: 呼び出し側の per-file 検証がすでに検出する不一致は、per-file 側を優先する

## 呼び出し側が定める項目

| 項目                 | 説明                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------ |
| 走査対象             | 主張を抽出するファイルの集合。巡回の分割や、直近の実装差分からの逆引きを使う場合は、その方法も指定する |
| 突合先               | 実装側として読むパス（コード・設定・要件）                                                             |
| 編集可能スコープ     | 記述修正を適用してよいパスの集合。それ以外は記録のみ                                                   |
| 記述層・規範層の範囲 | 走査対象のうち、規範層に当たるもの（既定は `docs/styles/coding_guide/docs.md` の層の表）               |
| 報告先               | PR 本文の該当区分（記述修正の一覧と「実装側判断要」）                                                  |
