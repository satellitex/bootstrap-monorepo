# daily-implement — 自動実装ラベルの付いた Issue を実装する

GitHub の open Issue に付いた `auto-implement` を着手指示として扱う。人が起票した Issue、保守 routine の提案、他の受付経路から起票した Issue は、すべてこのキューで扱う。各受付で着手条件を確認し、実装を依頼する時点で共通ラベルを付ける。ラベル名と優先度は [Project のラベル体系](../../../.claude/skills/create-issue/references/project-fields.md#ラベル体系) に従う。

自動実装はリポジトリごとに `/daily-implement` の一つのキューで受け付ける。

`/daily-implement --dry-run` は候補と既存の着手・PR を照合し、予定を報告する。ラベル・コメント・ブランチ・PR の変更、実装、外部通知はすべて省く。

## 対象を選ぶ

1. 同じリポジトリの自動実装は、起票経路を問わず、手動 run を含め一つの直列枠で処理する。前回の run と並行して同じ Issue に着手すると、両方が着手ラベルを付けられるためである。
2. [gh 照会の共通規約](shared/gh-query-fail-closed.md) に従って Issue、ラベル、関連 PR の読み取りを確認する。open Issue と open PR を全ページ取得し、Issue 一覧から PR を除き、`auto-implement` が付いたものを抽出する。選定は GitHub の記録で完結する。読み取りを完了して対象が 0 件なら「対象なし」で終了する。
3. open PR の closing keyword、Issue との関連付け、以前の着手記録と作業ブランチを照合する。該当する PR があれば新しい実装を始めず、その URL を報告に使う。`implementing` が残っている Issue は、前回 run の終了と GitHub 上の作業記録（PR、作業ブランチ、Issue のコメントやラベル履歴）を照合する。実行中か判定できなければ着手中として保留する。途中終了を確認できれば既存の作業を引き継ぐ。引き継げない場合は理由を記録し、下表の「実装を継続できない」と同じ処理をする。
4. 受入条件を対象開発ブランチの最新の内容と照合する。条件がすべて実現済みなら、条件ごとの commit・PR 等の根拠を Issue に記録し、対象ラベルを外して実装済みとして報告する。依存先が未解決のものは、待ち相手を記録して延期する。
5. 残った候補を優先度順、同順位なら作成日時の古い順に選ぶ。件数は [multi-issue](multi-issue.md) の in-flight 上限に従い、実装中・PR 保留中・レビュー待ちが使う枠を差し引く。枠を超えた候補と変更範囲が競合する後続は次の run に残す。実装の直前に open 状態、内容、対象ラベル、対応 PR を読み直して変化がなければ `implementing` を付け、読み戻す。

## 実装と結果の記録

選んだ Issue の実装には導入先で登録した処理を使う。既定は [multi-issue](multi-issue.md) で、このセッションが Planner として計画・実装・検証・レビュー・PR 作成まで進める。既存の実装処理を使う場合も、候補選定とスケジュールはこのキューに集約する。承認が必要な操作は [承認モデル](../OPERATING_MODEL.md) に従う。自動実装ラベルが委任するのは Issue の実装である。PR のマージと本番反映には導入先の既存手順と明示的な委任を適用する。

| GitHub で確認した結果 | Issue ごとの処理                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| PR が open            | 対象開発ブランチ向けの PR が Issue と対応し、closing keyword が正しいことを確認する。マージ結果または保留理由を確認し、人の対応待ちならこの状態で引き渡す     |
| PR がマージ済み       | 対応する PR のマージと Issue の状態を照合し、PR の URL を報告する                                                         |
| 次回へ延期            | 自動実装ラベルを維持し、延期した理由を報告する                                                                            |
| 実装を継続できない    | 既存 PR の URL、理由、再開条件を Issue にコメントし、自動実装ラベルを外す。条件が整いラベルが付け直されたら再び対象になる |

着手中（`claimed`）は着手ラベル、PR 作成済み（`pr`）は関連 PR で追跡する。延期（`deferred`）、失敗（`failed`）、人の作業待ち（`needs-human`）は再開条件とともに報告し、介入が必要な事項は Issue に記録する。GitHub に結果が残ったことを確認してから着手ラベルを外す。途中で終了した場合は次の run が同じ Issue と PR を照合し、残ったラベル更新や報告だけを補う。結果のコメントがすでにある場合は再投稿を省く。

opt-in:chat-feedback を併用する場合、受付の印がある Issue の結果を [元スレッドへの返信手順](shared/chat-feedback.md) に渡す。未設定や送信失敗は未送信として報告し、GitHub での実装と後処理を続ける。

完了報告に対象 Issue、既存・作成・マージした PR、延期や見送りと理由、残った着手ラベル・未送信の結果を記載する。対象があった run は [情報通知](shared/notification-contract.md) の契約に従って運用担当へ結果を送る。
