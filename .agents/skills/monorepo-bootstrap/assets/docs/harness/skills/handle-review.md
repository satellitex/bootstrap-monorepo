# handle-review — レビューコメントの批判的評価と自律対応

この文書は `/handle-review` の tool-neutral な正本手順である。検証ゲートの組合せの定義は `docs/harness/skills/shared/verification-gates.md` に一元化されており、ここには複製しない。

## 目的

PR レビューコメントを取得し、批判的に評価した上で自律的に対応する。修正・テスト・push・スレッドへの返信と resolve・ADR 記録を人間承認なしで一貫して実行する。

## 原則

コメントは必ずしも正しくない。各コメントに対して以下を検証してから対応を決める:

1. Best practice との整合性: 該当フレームワーク/ライブラリの公式ドキュメントと一致するか
2. 既存コーディングスタイルとの整合性: プロジェクト内の既存コードと矛盾しないか
3. 技術的正確性: コメントの前提や主張が事実として正しいか
4. スコープの妥当性: 指摘が PR の変更範囲に対して適切か（scope creep でないか）

## 入力

| 項目 | 必須 | 説明 | 例 |
|------|------|------|----|
| PR 番号 | No | 対象 PR。省略時は現在ブランチの PR を自動検出 | `/handle-review #<N>` |

## フロー

```
/handle-review [#PR]
  ├─ 1. PR 特定とコメント取得
  ├─ 2. 前処理（ADR ルックアップ・重複グルーピング）
  ├─ 3. コメント分析と対応方針の策定（自律判断・first-match 判定表）
  ├─ 4. 修正実装 + スレッドへの返信と resolve
  ├─ 5. 検証ゲートの実行
  ├─ 6. コミット・push（修正がある場合のみ）
  ├─ 7. ADR 記録（起票基準に該当する場合のみ）
  └─ 8. 結果サマリ出力（Comment ID 付き）
```

## Step 1: PR 特定とコメント取得

PR 番号が未指定の場合、現在のブランチから PR を自動検出する。

以下を取得する。各項目には、サマリで突合するための Comment ID を付ける（`rc:<id>` = review comment、`rv:<id>` = レビュー本体、`ic:<id>` = issue コメント）。

1. 未解決のレビューコメント（スレッド）
2. `CHANGES_REQUESTED` レビュー（本文付き）
3. 本文付きの `COMMENTED` レビュー（bot からの指摘を含む）。本文が空のもの（GitHub が line comment 時に自動生成するレビュー）は除外する

非アクション CI noise filter:

取得したコメント・レビュー body のうち以下は処理対象から除外する。除外時は「CI noise」として件数だけ Step 8 サマリに含め、本文を追加コンテキストに貼り付けない。マーカー文字列は PJ の CI レビュー bot / 自動コメント bot のマーカーに合わせて bootstrap 時に調整する。

- IaC plan 等の機械生成コメント（bot が固定 HTML コメントマーカーを付ける場合はそれで判定する）
- CI レビュー bot の auto マーカー付きコメントで本文が `LGTM` のみのもの（`/review-cycle` から呼ばれた場合、呼び出し元が終了判定用の auto LGTM シグナルとして保持した上で、本 skill には渡さない）
- GitHub Actions の check status / workflow log 通知のみで、file / line / fix suggestion を含まない CI イベント

機械生成コメントの詳細確認が必要な場合は、PR コメント本文ではなく artifact / workflow run URL を開き、必要な差分・エラー行だけを読む。

`/review-cycle` から呼ばれた場合、処理対象の Comment ID が渡されることがある。その場合は指定された ID のレビューのみを対象とする。

すべて 0 件の場合は「未解決のコメントはありません」と報告して終了する。

## Step 2: 前処理

### 2.1: ADR ルックアップ

`docs/adr/` 配下の既存 ADR を検索し、今回のコメントと一致する既知の判断がないか確認する。既存 ADR でカバー済みの指摘は「ADR 既決」として、4 軸評価とティア分類より先に確定する（Step 3.3 の判定表の行 1）。ADR で決着済みの指摘が、軸評価の結果次第で修正や Issue 化に流れるのを防ぐため。

既存の ADR が実態と合わなくなっている場合は、指摘への対応で吸収せず、`/create-adr`（`docs/harness/skills/create-adr.md` の Step 4）で置換の ADR を起票し、元の ADR の Status を更新する。

### 2.2: 重複グルーピング

同一ファイル・同一パターンへの複数コメントをグループ化し、バッチで対応する。例: 「import 順序」の指摘が 5 ファイルにある → 1 つの修正タスクとして扱う。

## Step 3: コメント分析と対応方針の策定

各コメント（グループ）に対して以下の評価を自律的に行う。

### 3.1: Reviewer 種別の判定

| 種別 | 判定基準 | 評価方針 |
|------|---------|---------|
| Bot | author が `*[bot]` または `*-bot` にマッチ | 4 軸すべて厳密に検証。false positive が多い |
| Human | 上記以外 | 意図を尊重しつつ 4 軸で検証 |

### 3.2: Severity ティア分類

| ティア | 対象 | 対応 |
|--------|------|------|
| T1: Must Fix | セキュリティ脆弱性、データ損失リスク、仕様違反 | 無条件で修正 |
| T2: Should Fix | バグ（機能不全）、型エラー、テスト不足 | 根拠が正しければ修正 |
| T3: Consider | 改善提案、リファクタリング、パフォーマンス | 調査の上で判断。スコープ外なら Issue 化 |
| T4: Preference | スタイル、命名、コメント追加 | 既存スタイルと照合。矛盾なら既存を優先 |

### 3.3: 4 軸評価と構造化判定

| 軸 | 判定 | 意味 |
|----|------|------|
| Best Practice | `✓` / `✗` | 公式ドキュメントと整合 |
| Style | `✓` / `△` / `✗` | プロジェクト既存パターンと整合 |
| Technical | `✓` / `✗` | 前提が事実として正しい |
| Scope | `✓` / `✗` | Issue の受入条件（AC）内 |

判定は次の表を上から評価し、最初に一致した行を採る（first-match）。どの軸の組合せも、ちょうど 1 行に当たる。

| 順 | 条件 | 判定 | 理由 |
|----|------|------|------|
| 1 | ADR 既決（Step 2.1） | 対応しない（ADR を返信で参照） | 決着済みの判断を覆さない。全軸が `✓` でも修正せず、Scope `✗` でも Issue 化しない |
| 2 | Technical `✗` | 対応しない（事実と異なる点を返信） | 前提が誤った指摘を修正や Issue にしない |
| 3 | Scope `✗` | Issue 化して対応しない | 本 PR の範囲外は別 Issue で追跡する |
| 4 | T1 | 修正する | 行 2・3 を通過しているため、残る `✗` は Best Practice / Style のみ。T1 は無条件で修正し、Style は既存パターンに合わせた形で直す |
| 5 | Best Practice `✗` | 対応しない（公式ドキュメントとの不整合を返信） | 公式の推奨と整合しない変更を入れない |
| 6 | Style `✗` かつ T3 / T4 | 対応しない（既存スタイルを優先する旨を返信） | 好みの違いより既存パターンの一貫性を優先する |
| 7 | Style `✗` かつ T2 | 修正する（既存パターンに合わせた形で） | 指摘の核は機能不全であり、提案の書き方ではなく問題そのものを直す |
| 8 | Bot かつ T3 / T4 かつ Style `△` | 対応しない | Bot の提案は false positive が多く、既存パターンと完全に整合しないものは採らない |
| 9 | Best Practice `✓` かつ Style `✓` | 修正する | 全軸が整合している |
| 10 | Best Practice `✓` かつ Style `△`（行 8 以外: Human、または Bot の T2） | 修正する | 軽微なスタイル差は既存パターンに合わせて直せる |

軸の値を 1 つに決められないコメントは、保守的 default（既存 docs → 一次情報 → 業界標準 → 現状の仕様を変えない案）で解釈を 1 つ選び、その解釈で軸の値を確定してから表を当てる（`docs/styles/team-feedback/autonomous-flow.md`）。

### 3.4: スコープ境界の判定

コメントが Issue のスコープを超える場合は対応しない。判定基準:

- Issue の受入条件（AC）に含まれない改善か？
- 後続タスクで自然に対応される内容か？

スコープ外の対応: 関連 Issue に追記、またはなければ `/create-issue`（`docs/harness/skills/create-issue.md`）で新規 Issue を作成して追跡する（`docs/styles/team-feedback/scope-boundary.md`）。

### 3.5: 調査項目

改善提案やスタイル指摘に対しては、判断前に以下を調査する:

- フレームワーク/ライブラリの公式ドキュメント・ソースコード
- プロジェクト内の既存コードにおける同種のパターン
- 該当する要件ドキュメント（`docs/requirements/` 配下）

## Step 4: 修正実装と返信

対応方針に従い修正を実施する:

- 修正は最小限に留める（指摘箇所以外のコードを変更しない）
- 既存テストが壊れないことを確認する
- 新規テストが必要な場合は追加する

返信はコメントのスレッドに投稿し、投稿後にスレッドを resolve する（GitHub API の `addPullRequestReviewThreadReply` と `resolveReviewThread`、または MCP）。PR 全体へのコメントで返さない。スレッドへの返信が無いと、後続の判定が同じ指摘を毎回再抽出し、返信済みかを機械的に判定できないため。スレッドを持たない `rv:` と `ic:` は、対象の Comment ID を引用した PR コメントで返信する。

- 対応しない・Issue 化と判定したコメント: 次の構造化フォーマットで理由を返信する
- 修正したコメント: push 後に、コミット SHA を添えて返信する

```
**対応不要**
- 軸: {ADR 既決 | Technical ✗ | Scope ✗ | Best Practice ✗ | Style ✗}
- 理由: {具体的な根拠}
- 参照: {ADR ファイル名 | Issue 番号 | ドキュメントリンク}（該当する場合）
```

## Step 5: 検証ゲートの実行

`gate:commit`（定義 → `docs/harness/skills/shared/verification-gates.md`）を実行する。format 検査で問題がある場合は修正してから次に進む。

## Step 6: コミット・push

修正内容をコミットし push する。コミットメッセージは修正内容を反映する。

修正がない場合（全コメントが「対応不要」）はこのステップをスキップする。

## Step 7: ADR 記録

`docs/adr/README.md` の起票基準（`docs/harness/skills/create-adr.md` の「起票基準」）に該当する場合に限り、`/create-adr` で ADR を記録する:

- 設計上の判断を伴う修正をした場合（判断根拠を記録）
- 複数案を比較して方針を決めた、または既存方針を撤回・置換した場合

スタイル指摘や事実誤認の却下などの軽微な「対応不要」判定は、Step 4 の返信に理由を書くだけで足り、ADR は作らない（判断ごとに ADR を作ると一覧と圧縮の負荷だけが増えるため）。

ADR の Author は `Agent (Review Comment)` とする。

## Step 8: 結果サマリ出力

対応結果をコンソールに出力する:

```
## Review Handling Summary

| # | Comment ID | Comment | Tier | Decision | Axis |
|---|------------|---------|------|----------|------|
| 1 | rc:<id> | {要約} | T1 | Fixed | ✓✓✓✓ |
| 2 | rv:<id> | {要約} | T4 | Skipped (ADR 既決: ADR-<date>_<slug>) | —✓✓✗ |
| 3 | ic:<id> | {要約} | T3 | Issue #<N> created | ✓✓✓✗ |

Changes committed: Yes / No
CI noise skipped: N
```

Axis 列は Best Practice・Style・Technical・Scope の順に値を並べる。このサマリは `/review-cycle` がループ判定に使用する。Comment ID は、呼び出し元が処理済みの指摘を管理して同じ指摘を再処理しないために使う。

## 制約

- 検証ゲート（`gate:commit`）をコミット前に実行する
- `--no-verify` を使わない。hook や検証が失敗したら原因を直す
- コメント対応の scope を超えた変更をしない
- 人間承認ゲートなし。全判断を自律的に行い、サマリで報告する（`docs/styles/team-feedback/review-comments.md`）
