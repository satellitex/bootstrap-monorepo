# handle-review — レビューコメントの批判的評価と自律対応

この文書は `/handle-review` の tool-neutral な正本手順である。検証ゲートのコマンド定義は `docs/harness/skills/shared/verification-gates.md` に一元化されており、ここには複製しない。

## 目的

PR レビューコメントを取得し、批判的に評価した上で自律的に対応する。修正・テスト・push・ADR 記録を人間承認なしで一貫して実行する。

## 原則

**コメントは必ずしも正しくない。** 各コメントに対して以下を検証してから対応を決める:

1. **Best practice との整合性**: 該当フレームワーク/ライブラリの公式ドキュメントと一致するか
2. **既存コーディングスタイルとの整合性**: プロジェクト内の既存コードと矛盾しないか
3. **技術的正確性**: コメントの前提や主張が事実として正しいか
4. **スコープの妥当性**: 指摘が PR の変更範囲に対して適切か（scope creep でないか）

## 入力

| 項目 | 必須 | 説明 | 例 |
|------|------|------|----|
| PR 番号 | No | 対象 PR。省略時は現在ブランチの PR を自動検出 | `/handle-review #<N>` |

## フロー

```
/handle-review [#PR]
  ├─ 1. PR 特定とコメント取得
  ├─ 2. 前処理（ADR ルックアップ・重複グルーピング）
  ├─ 3. コメント分析と対応方針の策定（自律判断）
  ├─ 4. 修正実装 + 「対応不要」コメントへの PR 回答
  ├─ 5. 検証ゲートの実行
  ├─ 6. コミット・push（修正がある場合のみ）
  ├─ 7. ADR 記録（判断事項がある場合）
  └─ 8. 結果サマリ出力
```

## Step 1: PR 特定とコメント取得

PR 番号が未指定の場合、現在のブランチから PR を自動検出する。

以下を取得する:

1. 未解決のレビューコメント（スレッド）
2. `CHANGES_REQUESTED` レビュー（本文付き）
3. **本文付きの `COMMENTED` レビュー**（bot からの指摘を含む）— 本文が空のもの（GitHub が line comment 時に自動生成するレビュー）は除外

**非アクション CI noise filter（必須）:**

取得したコメント・レビュー body のうち以下は処理対象から除外する。除外時は「CI noise」として件数だけ Step 8 サマリに含め、本文を追加コンテキストに貼り付けない。マーカー文字列は **PJ の CI レビュー bot / 自動コメント bot のマーカーに合わせて bootstrap 時に調整する**。

- IaC plan 等の機械生成コメント（bot が固定 HTML コメントマーカーを付ける場合はそれで判定する）
- CI レビュー bot の auto マーカー付きコメントで本文が `LGTM` のみのもの（`/review-cycle` から呼ばれた場合、呼び出し元が終了判定用の auto LGTM シグナルとして保持した上で、本 skill には渡さない）
- GitHub Actions の check status / workflow log 通知のみで、file / line / fix suggestion を含まない CI イベント

機械生成コメントの詳細確認が必要な場合は、PR コメント本文ではなく artifact / workflow run URL を開き、必要な差分・エラー行だけを読む。

`/review-cycle` から呼ばれた場合、処理対象のレビュー ID が渡されることがある。その場合は指定された ID のレビューのみを対象とする。

すべて 0 件の場合は「未解決のコメントはありません」と報告して終了する。

## Step 2: 前処理

### 2.1: ADR ルックアップ

`docs/adr/` 配下の既存 ADR を検索し、今回のコメントと一致する既知の判断がないか確認する。既存 ADR でカバー済みの指摘は Step 3 で「対応不要（ADR 既決）」として自動スキップする。

### 2.2: 重複グルーピング

同一ファイル・同一パターンへの複数コメントをグループ化し、バッチで対応する。例: 「import 順序」の指摘が 5 ファイルにある → 1 つの修正タスクとして扱う。

## Step 3: コメント分析と対応方針の策定

各コメント（グループ）に対して以下の評価を**自律的に**行う。

### 3.1: Reviewer 種別の判定

| 種別 | 判定基準 | 評価方針 |
|------|---------|---------|
| Bot | author が `*[bot]` または `*-bot` にマッチ | 4 軸すべて厳密に検証。false positive が多い |
| Human | 上記以外 | 意図を尊重しつつ 4 軸で検証 |

### 3.2: Severity ティア分類

| ティア | 対象 | 対応 |
|--------|------|------|
| **T1: Must Fix** | セキュリティ脆弱性、データ損失リスク、仕様違反 | 無条件で修正 |
| **T2: Should Fix** | バグ（機能不全）、型エラー、テスト不足 | 根拠が正しければ修正 |
| **T3: Consider** | 改善提案、リファクタリング、パフォーマンス | 調査の上で判断。スコープ外なら Issue 化 |
| **T4: Preference** | スタイル、命名、コメント追加 | 既存スタイルと照合。矛盾なら既存を優先 |

### 3.3: 4 軸評価と構造化判定

| 軸 | 判定 | 意味 |
|----|------|------|
| Best Practice | `✓` / `✗` | 公式ドキュメントと整合 |
| Style | `✓` / `△` / `✗` | プロジェクト既存パターンと整合 |
| Technical | `✓` / `✗` | 前提が事実として正しい |
| Scope | `✓` / `✗` | Issue の受入条件（AC）内 |

**判定ロジック:**

- 全 `✓` → 修正する
- Scope `✗` → Issue 化して対応しない
- Technical `✗` → 対応しない（理由を PR コメントで回答）
- ADR 既決 → 対応しない（該当 ADR を PR コメントで回答）
- Bot かつ T3/T4 かつ いずれかの軸が `✗` → 対応しない

### 3.4: スコープ境界の判定

コメントが Issue のスコープを超える場合は対応しない。判定基準:

- Issue の受入条件（AC）に含まれない改善か？
- 後続タスクで自然に対応される内容か？

**スコープ外の対応:** 関連 Issue に追記、またはなければ `/create-issue`（`docs/harness/skills/create-issue.md`）で新規 Issue を作成して追跡する（`docs/styles/team-feedback/scope-boundary.md`）。

### 3.5: 調査項目

改善提案やスタイル指摘に対しては、判断前に以下を調査する:

- フレームワーク/ライブラリの公式ドキュメント・ソースコード
- プロジェクト内の既存コードにおける同種のパターン
- 該当する要件ドキュメント（`docs/requirements/` 配下）

## Step 4: 修正実装

対応方針に従い修正を実施する:

- 修正は最小限に留める（指摘箇所以外のコードを変更しない）
- 既存テストが壊れないことを確認する
- 新規テストが必要な場合は追加する

「対応不要」と判定したコメントには、PR コメントで構造化フォーマットの理由を回答する:

```
**対応不要**
- 軸: {Scope ✗ | Technical ✗ | ADR 既決}
- 理由: {具体的な根拠}
- 参照: {ADR ファイル名 | Issue 番号 | ドキュメントリンク}（該当する場合）
```

## Step 5: 検証ゲートの実行

`docs/harness/skills/shared/verification-gates.md` に定義された全コマンドを実行する。format 検査で問題がある場合は修正してから次に進む。

## Step 6: コミット・push

修正内容をコミットし push する。コミットメッセージは修正内容を反映する。

修正がない場合（全コメントが「対応不要」）はこのステップをスキップする。

## Step 7: ADR 記録

以下の場合に `/create-adr`（`docs/harness/skills/create-adr.md`）で ADR を記録する:

- コメントを対応しないと判断した場合（却下理由を記録）
- 設計上の判断を伴う修正をした場合（判断根拠を記録）

ADR の Author は `Agent (Review Comment)` とする。

## Step 8: 結果サマリ出力

対応結果をコンソールに出力する:

```
## Review Handling Summary

| # | Comment | Tier | Decision | Axis |
|---|---------|------|----------|------|
| 1 | {要約} | T1 | Fixed | ✓✓✓✓ |
| 2 | {要約} | T4 | Skipped (ADR 既決: ADR-<date>_<slug>) | —✓✓✗ |
| 3 | {要約} | T3 | Issue #<N> created | ✓✓✓✗ |

Changes committed: Yes / No
CI noise skipped: N
```

このサマリは `/review-cycle` がループ判定に使用する。

## 制約

- 検証ゲート（`docs/harness/skills/shared/verification-gates.md`）をコミット前に必ず実行する
- `--no-verify` 禁止
- コメント対応の scope を超えた変更をしない
- 人間承認ゲートなし — 全判断を自律的に行い、サマリで報告する（`docs/styles/team-feedback/review-comments.md`）
