# feedback-triage — チャットの要望を Issue にし、対応結果を元スレッドに返す

受付先ごとに [profile](../../../.claude/skills/feedback-triage/references/chat-profile.md) を読み、[チャットの共通契約](shared/chat-feedback.md) に従う。`/feedback-triage --dry-run` は読み取りと判定までを行い、チャットへの送信・リアクション・Issue の変更をすべて省く。

## 1. 受付を読む

1. `whoami` と profile で bot と受付先を照合する。承認者が登録済みであり、bot 自身が含まれていないことを確かめる。
2. `history` で profile の収集期間内の親投稿を読み、bot とシステムの投稿を除く。過去に起票済みで通知が終わっていない項目は、収集期間を過ぎても Issue・コメントの印から親を特定して `replies` で追跡する。長く承認待ちだった未起票の案を再開するときは、開始時刻をその親投稿までさかのぼらせる。
3. 同じ人が 10 分以内に続けた親投稿は、途中にほかの人の投稿がなく、同じ依頼の補足で、後の投稿に独立した会話がなければ、先の投稿にまとめる。後の投稿には `[まとめ]` で受付先スレッドのリンクを返す。再実行では既存の `[まとめ]` に従い、後の投稿に追加の人間の返信があればそれも元の依頼に取り込む。添付は実際の投稿 ID で読む。
4. 返信のある親ではスレッドを読み、bot が 👀 を付けていない人間の発言と、最新の案へのリアクションを確認する。bot が 🏁 を付けたスレッドは、新しい要望を別の親投稿で受け付ける。読了・完了印は `users` に当該 bot の user ID があるものだけが有効。読むべき履歴・承認を取得できなかった場合は、その受付の書き込みを始める前に失敗を報告する。

## 2. 項目ごとに案を返す

同じ原因を持つ要望は 1 項目にまとめ、個別に採否を決められる変更には別々の番号を付ける。添付は `file` の一時保存先で確認し、スクリーンショットの表示や文書の要点を文章にする。音声・動画・10 MiB を超える添付は取得を省く。取得・解読できない添付は理由を記す。本文・添付・既存の実装や docs から変更箇所を特定し、推定した条件は案で明示する。

- 要望を特定できたら、open の Issue に同じ受入条件があるか照合し、新規起票または既存 Issue への追記を提案する。案には実装担当を示す。`/daily-implement` に実装を委任し、その対象条件を満たすときだけ自動実装を提案する。自動実装を委任していない場合、課金・秘密値・人間への引き渡し・外部の回答待ちがある場合は、理由を添えて自動実装の対象外とする。追記を提案する場合は、既存 Issue がキューに入っているかも明記する。
- 情報が足りず変更を特定できない場合は `[質問]` で不足する事実を 1 つ尋ねる。感想や使い方の質問には `[対象外]` と理由を返す。複数の案を出したら、案ごとに 1 通で返信する。

```text
[起票案 <n>] <変更のタイトル>
背景と内容　<観察された事実と変更内容。推定した点を明示>
受入条件　<実装後に確認できる条件>
対応先　<新規 Issue または既存 Issue の番号と追記する内容>
自動実装　<対象または対象外と理由>
この案で進める場合は ✅、見送る場合は ❌ をこの返信に付けてください。訂正はスレッドに書けます。
対象投稿 <投稿ID>
```

返信の後に各入力へ 👀 を付ける。途中で停止したら、既存の案と対象投稿 ID を照合し、既出項目の番号を維持して未送信の項目だけを返す。承認・回答を待つ項目は次回の実行に残す。

## 3. 会話と承認を反映する

| 状態                   | 新しい入力と処理                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 起票前                 | 訂正には同じ番号で改訂した案を新規返信する。承認は改訂版へのものだけが有効。投稿者または承認者からの取り下げは `[取り下げ n]` で記録する |
| 最新の起票案が承認済み | Issue の作成または承認された既存 Issue への追記に進む                                                                                    |
| 最新の案が否決         | 起票案は見送り、修正案は棄却して直前の Issue の状態に戻す。他の項目を続ける                                                              |
| 起票済み・実装前       | 承認者が書いた訂正はその内容を反映する。他の人の訂正・取り下げは変更箇所と対象 Issue を示した `[修正案 n]` を返し、承認後に反映する      |
| 実装着手後             | 着手ラベル、対応する PR、またはマージを確認した後の追加・変更・取り下げは、元 Issue にリンクした新しい案として扱う                       |

承認済みの変更は次の順で適用する。

1. 共通契約に従って既存の印と必要なラベルを照合する。書き込み直前にスレッドを読み直し、未読の訂正を先に扱う。起票案・修正案の採否は、照合した案の返信 ID と profile の承認者だけを `decision` に渡して確認する。`pending` は保留、`superseded` は最新状態から再判定する。承認者本人が直接訂正した場合はその発言の user ID・対象・内容を確認する。GitHub の照会が不完全なら書き込みを見送る。
2. 新規 Issue は [create-issue](create-issue.md) に承認済みの内容、元投稿へのリンク、末尾の印、出所と routine のラベルを渡す。自動実装が承認された新規 Issue は、ほかの起票経路と共通の対象ラベル（既定 `auto-implement`）を付けて `/daily-implement` に渡す。別の受付先が先に同じ変更を起票していれば、同じ条件を既存 Issue に追記する。追記は印付きコメントで行い、既存 Issue のラベルを引き継ぐ。
3. 訂正時には実装がまだ始まっていないことを再照会する。新規起票分はタイトル・受入条件・自動実装の対象を更新し、印を保つ。単独の依頼を取り下げたら未計画として閉じる。既存 Issue への追記分や他の有効な依頼も含む Issue は、その項目の記述とコメントだけを更新し、取り下げの記録にも印を残す。
4. Issue・コメント・ラベルを読み戻し、元スレッドに `[起票済み n]`、`[更新済み n]`、`[取り下げ n]` のいずれかと Issue のリンクを返す。編集が必要な Issue の版や関連付けが変わっていた場合は、最新状態から再判定する。

## 4. 実装・本番反映を確認する

チャット受付だけを導入した場合も、手動で作成された PR と配備結果を追跡する。Issue の本文またはコメントにある有効な印ごとに、元スレッドの返信と GitHub の記録を照合する。`/daily-implement` が処理した Issue も同じ方法で追跡し、実装時に届けられなかった結果を補う。

1. まだ完了していない各項目について、Issue を閉じる PR の関連付け、対象リポジトリ、base、実際のマージ状態を確かめる。単に人が Issue を閉じただけの場合はマージを報告しない。対応する PR が開いていれば `[PR作成 n]`、マージ済みなら `[マージ済み n]` とその PR のリンクを、不足する場合に返す。実装が見送られた場合は運用担当が記録した理由を返す。
2. マージ済みの変更が本番に含まれるかを、profile の配備記録で調べる。確認には導入先のリリース手順を使い、`/deploy-verify` 採用先ではその配備後の確認に従う。対象環境・配備済みの SHA または成果物と PR の対応・導入先で必須の配備処理と検証の成功を確認する。`release` ブランチへの到達、タグ、無関係な最新リリースだけで反映済みと判定しない。該当する記録がまだない、確認できない、またはロールバック済みなら保留する。
3. 確認できた項目に `[本番反映 n]` と該当する配備記録の URL を返す。本番配備のないプロジェクトでは、profile の配布完了条件を満たしたときに `[配布完了 n]` と対象バージョン・配布記録の URL を返す。見送り・取り下げ・対象外・配布完了で全項目が終わり、未読もなければ親に 🏁 を付ける。実装見送り後に再開する予定がある項目は開いたままにする。

## 報告

処理した親投稿・項目の件数、Issue / PR / 配備記録の URL、承認・回答待ちのスレッド、未確認の添付・配備、失敗と再開箇所を報告する。予定した操作だけを報告する dry-run、対象なし、取得失敗はそれぞれ区別する。
