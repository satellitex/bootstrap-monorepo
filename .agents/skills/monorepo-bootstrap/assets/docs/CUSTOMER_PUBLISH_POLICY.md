# 顧客向け公開ポリシー

> この文書は、内部ドキュメントを顧客向け（アプリ開発エンジニア・アーキテクト・SRE 等）に公開する際の判定基準と機械検査の運用ルールの正本である。
> 公開コンテンツの内容そのもの・ビルド実装の詳細はここに書かない。

公開対象は **認証で保護された統合ドキュメントサイト** とする。

## 1. 公開対象と区画

区画構成はプロジェクトごとに確定する。次は代表的な区画の例（採用時に実際の構成で書き換える）:

| 区画（例） | 種別 | ソース | 配信方式 |
|------|------|-------|---------|
| `/api` | コードリファレンス | API 実装から生成した OpenAPI JSON | OpenAPI ビューア |
| `/sdk` | コードリファレンス | SDK の doc コメント → ドキュメントジェネレータ | 生成 HTML |
| `/architecture` | 設計ドキュメント | `docs/product/PUBLIC_ARCHITECTURE.md`（`ARCHITECTURE.md` の公開射影） | markdown → サニタイズ済み HTML |
| `/quality` | 品質保証 / テスト網羅状況 | 要件 ↔ テストのトレーサビリティ成果物（opt-in:traceability 採用時） | 生成 HTML（内部参照 scrub 済み） |

- 設計ドキュメント区画はソース markdown を改変せず、ビルド時に「公開射影 HTML」を生成して配信する。
- サービス名の抽象化など機械サニタイズで吸収できない射影が必要な区画は、内部正本とは別に公開用の射影 markdown を `docs/product/` に置き、ドリフト防止 skill（`/public-arch-sync` → `docs/harness/skills/public-arch-sync.md`）で追従させる。
- 内部専用文書（`TECH_STACK.md` 等）はビルド対象から除外する（内部 docs として温存する）。

## 2. 機械検査される内部参照パターン

検査対象パターンは単一モジュールに集約し、ソースコメント lint と公開前 gate の双方から import する（二重定義しない）。

- パターン定義モジュール: `TODO(取得方法: 公開ビルド実装時に内部参照パターン定義モジュールのパスを確定して記載する)`

### 2.1 業務 ID

- **ADR**: `ADR-YYYYMMDD` 形式
- **要件 ID**: `BR|IF|DATA|FR|NFR|SEC-NNNN(-FIX)?`、および `US-NNNN` 形式
- **設計判断 ID**: `AC-NNN-NN` / task-note の設計判断 ID（`D1` 等の D-ID 表記）

### 2.2 Issue 参照

- `Issue #NNN` 形式（前置詞 "Issue " 付き）
- bare `#NNN` 形式（3 桁以上。`PKCS#8` 等の外部標準名とは区別）

### 2.3 内部 docs パス

- 基本対象: `docs/(adr|issues|product|notes|requirements)/`
- 公開前 gate の追加対象: `docs/(styles|harness|runbooks|audit|customer)/`

ソースコメント lint は基本対象のみを検査し、style guide 参照（`docs/styles/` 等）はコード内 doc コメントでは許容する。

### 2.4 検査対象外（false-positive 抑制）

以下は検査パターンに含めない:

- 外部標準仕様名: `RFC-NNN`, `ISO-NNNNN`, `PKCS#N`, `SHA-N` 等
- 外部 URL（`https://`, `http://`, `mailto:`）、同一文書内 anchor `#section`
- 2 桁以下の `#NN` 参照（コード / 表行番号との誤検出回避）

## 3. 新規 markdown を公開対象に追加する手順

1. ソース markdown を `docs/product/` 配下に配置する（社内向け原本のまま、内部参照を含んでよい）
2. 公開ビルド設定に新区画エントリ（配信 path・ソースパス・タイトル・対象読者）を追加する
3. 公開前 gate の検査対象 slug に新区画を追加する
4. ローカルでビルドと内部参照リーク検査を実行する
5. CI の公開 gate（docs 検査 workflow）が pass することを確認する

## 4. リーク検出時の対応（優先順位）

公開前 gate がリークを報告した場合、次の優先順位で対応する:

1. **ソース markdown 側の表現を差し替える**（最優先）
   - 該当箇所が「内部参照を載せる必要がない説明」なら ID を抜く
   - 例: `（FR-1003 / SEC-2002）の制約に従う` → `データ整合性制約に従う`
2. **サニタイズルールを拡張する**
   - 新規パターンが正規表現に未対応の場合、または特殊文脈（コードブロック内の図示等）で取り零している場合
3. **内部参照パターン定義を見直す**
   - 新規 ID 体系（新しい `XX-NNN` ファミリー）が登場した場合。拡張時は既存 lint との互換性が保たれることをテストで確認する

リーク報告は「生成 HTML のパス:行 `[internal-reference: <matched>]`」形式とし、`<matched>` を grep してソース markdown の該当箇所を特定してから上記順序で対応する。

## 5. 認証層

公開サイト全体は **fail-closed の認証**（Basic 認証等。認証設定が読めない場合は配信を拒否する構成）で保護する。新規区画は認証設定を変更せずに自動的に保護下へ入る構成とする。credential のローテーション手順は `docs/runbooks/` の該当 runbook に置く。

## 6. 図版とアセット

ソース markdown が相対パスで画像参照する場合、ビルド時に画像ディレクトリを配信先へコピーする。外部 URL への画像参照はサニタイザが外部リンクとして保持するため追加対応不要。
