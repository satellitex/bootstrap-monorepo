# リファクタリングガイド

> この文書は「いつ・何を・どこまで」リファクタすべきかの運用モデルと検出観点を定義する。
> 個別の言語規約・デザインパターン規約は [coding_guide](coding_guide/INDEX.md) が正本であり、本書には書かない。
> 検出コマンドの詳細・必読ガイド一覧は `.claude/agents/references/refactorer-profile.md`（プロジェクト profile）に分離する。

## 運用モデル

```
夜間自動: refactorer agent がコード課題を検出 → 観点ごとに Issue 提案（refactor:proposal ラベル）
着手指示: Issue に refactor:approved ラベルを付与 = 実装への着手指示
実装:     承認済み観点を本ガイド「承認済み観点」節へ追記し、既存テスト全 PASS を維持して
          全対象に順次適用、open PR まで自律実行
以降:     CI / レビューで観点を継続適用
```

- **1 Issue = 1 観点** — 複数の課題をまとめない。観点が異なれば別 Issue にする。
- **refactorer はコードを変更しない** — 指針・理由・影響範囲を提案するだけ。
- **refactor:approved ラベルが実装のトリガー** — このラベル付与は実装への**着手指示**（Issue アサインと同格の明示指示であり、承認ゲートではない）。自律実行モデル（[autonomous-flow](team-feedback/autonomous-flow.md)）で人間承認が必須なのは課金と秘密値の 2 つのみで、本ラベルはそのどちらにも該当しない。refactorer が提案するのは「候補」であり、どの観点にいつ着手するかは通常の作業依頼として指示される。指示後は open PR まで自律で進める。

## 原則

1. **テストが通る状態から始め、テストが通る状態で終える** — テストのないコードはリファクタリング対象外。先にテストを書く。
2. **1 PR = 1 リファクタリング観点** — 機能変更とリファクタリングを混ぜない。
3. **スコープは最小限** — 影響範囲を限定し、レビュー可能なサイズに保つ。
4. **機械的に検出、人間が判断** — lint / typecheck / grep で検出し、リファクタの要否は人間が判断する。

## 優先度マトリクス

| 優先度 | 分類 | 説明 | 例 |
|--------|------|------|-----|
| **Critical** | セキュリティ | 脆弱性に直結する課題 | 秘密情報のログ・エラーメッセージへの露出、型安全性の喪失による入力検証の迂回 |
| **Must** | ガイド違反 | コーディングガイドへの明確な違反 | 命名規則違反、公開 API のドキュメントコメント欠落 |
| **Should** | 可読性・保守性 | 理解やメンテナンスを妨げる課題 | 巨大関数、深いネスト、重複ロジック |
| **Nice** | スタイル統一 | 動作に影響しないが一貫性を損なう | import 順序、不要な空行 |

## 検出観点

検出観点は [coding_guide](coding_guide/INDEX.md) の各規約を根拠とする。スタック非依存の基本観点は以下の 5 つ。
言語・パターン別規約を追加したら、対応する検出観点と検出コマンドを `.claude/agents/references/refactorer-profile.md` に追記する（観点の網羅リスト・具体コマンドは同 profile が正本）。

| 観点 | 説明 | 優先度 |
|------|------|--------|
| 重複ロジック | 同一実装の関数・処理が複数箇所に定義されている | Should |
| 巨大関数・深いネスト | 1 関数が長大、または分岐ネストが深く読解困難 | Should |
| デッドコード | 未参照の関数・変数・未使用 export が残存している | Should |
| エラーの握り潰し | 例外を catch して無視、または生のエラー文字列で分岐している | Must |
| 型安全性の喪失 | 型チェックを無効化する記述（`any` 相当）が残存している | Critical |

## 禁止事項

- 機能変更の混入（振る舞いを変えるならそれは機能変更であり、別 PR にする）
- テストなしでのリファクタリング実行
- リンター・ハーネス設定ファイルの直接編集
- `--no-verify` の使用
- 推測での要件補完（不明点は Issue にする）
- 未承認の観点でのリファクタリング実行

## 検証手順

リファクタリング前後で、検証ゲート（`docs/harness/skills/shared/verification-gates.md` に定義されたコマンド一式）がすべてパスすること。リファクタ後のテスト結果がリファクタ前と同一であることを確認する。
