# リファクタリングガイド

> この文書は「いつ・何を・どこまで」リファクタすべきかの運用モデルと検出観点を定義する。
> 個別の言語規約・デザインパターン規約は [coding_guide](coding_guide/INDEX.md) が正本であり、本書には書かない。
> 検出コマンドの詳細・必読ガイド一覧は `.claude/agents/references/refactorer-profile.md`（プロジェクト profile）に分離する。

## 運用モデル

```
夜間自動: refactorer agent がコード課題を検出 → 観点ごとに Issue 提案（refactor:proposal ラベル）
着手指示: Issue に refactor:approved ラベルを付与 = 実装への着手指示
実装:     承認済み観点を本ガイド「承認済み観点」節へ追記し、既存テスト全 PASS を維持して
          全対象に順次適用、open PR まで自律実行
以降:     CI / レビューで観点を継続適用
```

- **1 Issue = 1 観点** — 複数の課題をまとめない。観点が異なれば別 Issue にする。
- **refactorer はコードを変更しない** — 指針・理由・影響範囲を提案するだけ。
- **refactor:approved ラベルが実装のトリガー** — このラベルの付与は実装への**着手指示**（Issue アサインと同格の明示指示）。本ラベルは承認ゲートではなく通常の作業依頼として扱う（承認が必須な操作 → `docs/harness/OPERATING_MODEL.md`「承認モデル」）。refactorer が提案するのは「候補」であり、どの観点にいつ着手するかは指示で決まる。指示後は open PR まで自律で進める。

## 原則

1. **テストが通る状態から始め、テストが通る状態で終える** — テストのないコードはリファクタリング対象外。先にテストを書く。
2. **1 PR = 1 リファクタリング観点** — 機能変更とリファクタリングを混ぜない。
3. **スコープは最小限** — 影響範囲を限定し、レビュー可能なサイズに保つ。
4. **機械的に検出、人間が判断** — lint / typecheck / grep で検出し、リファクタの要否は人間が判断する。

## 優先度マトリクス

| 優先度       | 分類           | 説明                             | 例                                                                           |
| ------------ | -------------- | -------------------------------- | ---------------------------------------------------------------------------- |
| **Critical** | セキュリティ   | 脆弱性に直結する課題             | 秘密情報のログ・エラーメッセージへの露出、型安全性の喪失による入力検証の迂回 |
| **Must**     | ガイド違反     | コーディングガイドへの明確な違反 | 命名規則違反、公開 API のドキュメントコメント欠落                            |
| **Should**   | 可読性・保守性 | 理解やメンテナンスを妨げる課題   | 巨大関数、深いネスト、重複ロジック                                           |
| **Nice**     | スタイル統一   | 動作に影響しないが一貫性を損なう | import 順序、不要な空行                                                      |

## 検出観点

検出観点は [coding_guide](coding_guide/INDEX.md) の各規約を根拠とする。スタック非依存の基本観点は以下の 5 つ。
言語・パターン別規約を追加したら、対応する検出観点と検出コマンドを `.claude/agents/references/refactorer-profile.md` に追記する（観点の網羅リスト・具体コマンドは同 profile が正本）。

| 観点                 | 説明                                                        | 優先度   |
| -------------------- | ----------------------------------------------------------- | -------- |
| 重複ロジック         | 同一実装の関数・処理が複数箇所に定義されている              | Should   |
| 巨大関数・深いネスト | 1 関数が長大、または分岐ネストが深く読解困難                | Should   |
| デッドコード         | 未参照の関数・変数・未使用 export が残存している            | Should   |
| エラーの握り潰し     | 例外を catch して無視、または生のエラー文字列で分岐している | Must     |
| 型安全性の喪失       | 型チェックを無効化する記述（`any` 相当）が残存している      | Critical |

### 検出方法の実効性

観点の検出方法に lint ルール名を書けるのは、共有 lint 設定で有効化済みのルールだけである。ルール名を書く前に、採用した lint ツールの有効設定の表示コマンドで有効性を確認する（コマンドは `.claude/agents/references/refactorer-profile.md` に記入する）。無効なルールを検出方法に書くと、手順どおりに実行しても常に検出 0 件となり、課題がない状態と区別できない。有効でない観点は、grep など実行可能な手段で書く。承認済み観点の「検出方法」欄にも同じ規則を適用する。

## コード量削減の観点

機能追加が積み重なると、規約には違反していなくても、振る舞いに効かないコードが増える。コード量を減らす観点として、次の 3 分類で扱う。優先度は Should。

「デッドコード」観点が参照 0 件のコードを扱うのに対し、本観点は参照が残っているが消しても振る舞いが変わらないコードを対象とする。

### 適用の条件

- 削減見込み行数を、テストを含むネットの行数で Issue に書く
- 公開 API・配布物に当たる候補は、削除が後方互換を壊すため、Issue と PR 本文に明示する
- 採用した設計パターン規約が要求する構造（interface・Adapter など）と、信頼境界の実行時検証は、削減候補にしない
- テストのアサーションの重複は対象外とする（[テスト設計原則](coding_guide/testing_principles.md) の「DAMP over DRY」）
- リポジトリで確かめられない前提に依存する候補は、起票しない

### 効いていないコード

| 観点                                 | 検出方法                                                       |
| ------------------------------------ | -------------------------------------------------------------- |
| 全呼び出し元が同じ値を渡している引数 | 呼び出し箇所を grep し、渡している値を集計する                 |
| 誰も指定しないオプションと、その分岐 | オプション名を grep し、指定している呼び出し元の有無を確認する |
| 読み取られない設定キー               | 設定スキーマのキーを列挙し、読み取り箇所を grep する           |
| 使われない依存                       | 依存宣言の各パッケージについて、import 箇所を grep する        |
| コメントアウトされたコード           | コメントマーカーの直後がコード構文の行を grep する             |
| 常に同じ結果になる型ガード・条件分岐 | 型情報から、常に真または常に偽になる条件を確認する             |

### 非推奨の残置

| 観点                           | 検出方法                                                               |
| ------------------------------ | ---------------------------------------------------------------------- |
| 呼び出し元が残る非推奨の別名   | 非推奨マーカーを grep し、後継への置換可否と呼び出し元を確認する       |
| 利用者がいなくなった互換レイヤ | 互換レイヤの参照元を grep し、互換対象の入力を渡す箇所の有無を確認する |
| 全環境で同じ値の feature flag  | 環境ごとの設定値を比較し、すべて同値なら分岐を一本化する               |

### 冗長なコード

| 観点                                             | 検出方法                                                                   |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| 重複ロジック                                     | 「重複ロジック」観点の検出方法に従う                                       |
| 標準 API・導入済みの依存・共通モジュールの再実装 | 自前実装の処理内容を、同等の標準 API・依存・共通モジュールの機能と照合する |
| 素通しの wrapper                                 | 本体の呼び出しだけを行う関数・クラスを確認する                             |
| 型定義から導出できる型の手書き再定義             | 同じ形の型定義が複数ある箇所を確認し、一方から他方を導出できるかを検討する |

## 守ること

- 機能変更を混ぜない。振る舞いを変える差分は別 PR にし、レビューで「変わらない差分」と「変わる差分」を分けて読めるようにする
- 既存テストを通した状態から始める。テストが無い箇所は、先に現状の振る舞いを固定するテストを足す
- リンター・ハーネス設定は変更せず、必要なら Issue にする（検出基準そのものが変わるため）
- 検証や hook の失敗は原因を直す（`--no-verify` で回避すると、`format:check` / `build` の失敗は CI で初めて赤くなり、`lint` / `typecheck` / 秘密検知の失敗は CI が実行しないため検出されないまま残り得る）
- 不明点は要件を推測で補わず、Issue にする
- 承認済み観点（`refactor:approved`）だけを対象にする（未承認の観点は着手指示がなく、レビュー負荷が読めない）

## 検証手順

リファクタリング前後で、検証ゲート（`docs/harness/skills/shared/verification-gates.md` に定義されたコマンド一式）がすべてパスすること。リファクタ後のテスト結果がリファクタ前と同一であることを確認する。
