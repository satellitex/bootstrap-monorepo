# PR を出す前にリファクタパスを 1 回入れる

> この文書は team-shared rule の 1 つ。PR 提出前の見直しパスの規範のみを定め、リファクタの検出基準は [refactoring_guide](../refactoring_guide.md)、PR 作成手順は `docs/harness/skills/shared/pr-creation.md` に書く。

実装が終わってテストが green になったら、**PR を作る前に**差分に対してリファクタパスを 1 回実行する。「動いたので出す」で止めない。

## Why

- 実装中は「原因を見つけて直す」ことに注意が集中するため、直した結果できた重複・条件分岐の肥大・不要な抽象がそのまま PR に乗りやすい
- レビュー段階でこれを指摘されると、レビュアの往復と修正 push が発生する。自分で 1 パス回す方が総コストが低い
- リファクタを機能変更と同じコミットに混ぜると、レビュアは「意味のある変更」と「移動しただけの行」を分離できず、レビュー精度が落ちる

## How to apply

`/multi-issue` は worker 実装後の簡素化パスを内包している。それ以外の実装（メインエージェント判断のバグ修正・小規模変更等）にはこのフェーズが存在しないため、PR 作成手順の直前に明示的に挟む。

1. **簡素化パスを実行する** — 変更差分を再利用性・簡潔さ・効率・抽象度の観点で見直し、修正まで適用する。実行環境に `/simplify` 相当の見直し skill があればそれを使い、無ければ [refactoring_guide](../refactoring_guide.md) の検出観点と [coding_guide/INDEX.md](../coding_guide/INDEX.md) を自分で当てて同等の見直しを行う（バグ探索はここではしない。それはコードレビューの責務）
2. **振る舞い不変を確認する** — リファクタ後に対象テストを再実行し、**リファクタ前と同じ結果**であることを確認する。ここでテストを直す必要が出たら、それはリファクタではなく仕様変更なので切り分ける
3. **リファクタは別コミットに分ける** — `refactor:` type で機能変更コミットと分離する。レビュー時に「振る舞いを変える差分」と「変えない差分」を独立して読めるようにする

適用しないケース:

- **1〜2 行の hotfix** など、差分が構造を持たず見直す対象が無い場合。この場合は task-note（`docs/issues/` 配下の記録）に「差分が小さくリファクタ対象なし」と記録して省略する
- **ハーネス開発（`.claude/**` / `docs/harness/**` の Markdown 変更）** — コードの再利用・効率の観点が当たらない。代わりにネット行数・二重化・閾値妥当性の観点で over-engineering を自己点検する
