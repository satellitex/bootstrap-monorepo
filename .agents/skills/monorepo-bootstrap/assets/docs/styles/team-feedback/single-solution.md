# 解決策は 1 案に確定して書く

> この文書は team-shared rule の 1 つ。解決策の選び方と、人間へ引き渡す範疇の扱いのみを定め、Issue 起票・PR 作成の具体手順は各 skill 正本（`docs/harness/skills/create-issue.md` ほか）に書く。

Issue・PR・計画を書く agent / skill は、解決策の候補が複数あっても選択肢のまま残さず、次の 3 条件を満たす案を 1 つ選んで確定事項として書く。選んだ案と理由は記録に残す。

| 条件 | 内容 |
|------|------|
| 現状の仕様を保つ | 公開契約・運用のふるまいなど、現行の仕様を変えない |
| 根本的 | 原因を取り除き、同じ種類の事象が再発しない |
| シンプル | 変更の範囲と、新しく足す仕組みが最小になる |

3 条件が両立しない場合は、現状の仕様を保つ案、根本的な案、シンプルな案の順に優先する。

## 人間へ引き渡す範疇

人間へ引き渡す範疇は、`docs/harness/OPERATING_MODEL.md` の承認モデル節「人間引き渡し境界」小節が定める。既定は「なし」で、その場合はすべての案を 1 案に確定して進める。導入先が境界を定めたときは、選んだ案がその境界に当たる場合に限り、案と根拠を記録して人間へ引き渡す。引き渡しの扱い（記録して続行 / 引き渡して終了）は実行モードによる（→ `docs/harness/skills/shared/unattended-contract.md`）。

課金と秘密値の承認は境界とは別であり、常に人間が行う（→ [autonomous-flow](./autonomous-flow.md)）。

## 書きたくなる項目と、書くもの

| 書きたくなる項目 | 書くもの |
|------------------|----------|
| 「A / B / C から選ぶ」「要否を判断する」 | 3 条件で選んだ案と、選んだ理由（退けた案を 1 行ずつ） |
| 「〜と判断した場合は〜する」 | 判断の材料を調べた結果と、それに基づいて決めた動作 |
| 「〜が意図したものか確認する」 | リポジトリ・CI ログ・読み取り専用の観測手段で確かめられる根拠と、その根拠からの結論。根拠が揃わない事象は、次に同じ事象が起きたときに機械的に判別できる仕組み（タグ・抑止条件・記録）の実装 |
| 「削除するか残すかを選ぶ」 | 検証を通った候補は削除、根拠付きで残す候補は残す理由を記した印、という確定した処置 |
| 手作業の運用操作 | 同じ操作を IaC・スクリプト・CI に置く実装。手作業でしか行えない一回限りの操作は、手順を runbook に置き、Issue の完了条件にしない |
| 「受入条件が満たされているか確認して close する」 | 満たされている根拠（commit / PR / ファイルの行）を書いて close する |

## Why

選択肢を残した Issue や計画は、実装側が判断待ちとして扱いやすく、着手されないまま滞留する。判断の材料の多くはリポジトリ・CI ログ・読み取り専用の観測手段で揃うため、書き手が確定すれば実装側は止まらずに進める。人間は PR のレビューとマージの段階で判断を覆せる。途中の判断を人間に預けて止めるより、確定した案を PR にする方が、人間の作業は 1 回のレビューで済む。

## How to apply

- Issue を起票する skill / agent（`/create-issue`、refactorer など）は、受入条件をリポジトリ内で満たせる確定事項として書く。「A か B かを選ぶ」は受入条件にしない
- Issue を実装するフロー（`/multi-issue`、メインエージェント判断）は、選択肢や判断待ちの項目が残る Issue を受け取ったら、3 条件で案を選び、選んだ案と理由を PR 本文の「方針と却下案」節に記録して実装する（PR 本文の構成 → `docs/harness/skills/shared/pr-creation.md`）
- 計画に「Open Questions」節を置かず、判断は上表に従って確定した形で書く
- 「人間承認推奨」として記録するのは、人間引き渡し境界に当たる案に限る（→ [autonomous-flow](./autonomous-flow.md)）
- Issue を close するときは、手動・自動を問わず、受入条件を満たす根拠を書く
