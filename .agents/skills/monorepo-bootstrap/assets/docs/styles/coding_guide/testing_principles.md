# テスト設計原則

> この文書は言語横断のテスト設計原則である。テストレベルの正式定義・CI 実行トリガーは [TEST_STRATEGY.md](../../product/TEST_STRATEGY.md) を正本とし、フレームワーク固有の書き方は各言語規約に書く。本書は「何をテストとして書くべきか / 書くべきでないか」の判断規範のみを定める。

## 第一原則: ユーザーストーリー起点

> テストは「ユーザーストーリーの設計」→「それに対応するテストのみを作成」の順で書く。ユーザーストーリーに対応しない冗長なテスト、数合わせのテスト、実装詳細に密結合してすぐ形骸化するテストは書かない。

- テストを書く前に、対象のユーザーストーリー（US）と受入条件（AC: Given / When / Then）を先に確定する
- 各テストケースは、どの US / AC を検証しているかを説明できること。説明できないテストは書かない
- カバレッジ数値や件数を目的にテストを増やさない。件数は結果であって目標ではない
- 実装の内部構造（private 関数・呼び出し順序）に密結合したテストは、リファクタで壊れて形骸化するため書かない

## テストピラミッド

上位ほど実行コストが高く外部依存が増え、下位ほど高速で隔離される。

| レベル | 比率目安 | 対象 | 外部依存の扱い |
|--------|---------|------|--------------|
| L1 Unit | 大半 | 関数・クラス単体のロジック | 実 I/O なし（時刻 / 乱数のみ Mock） |
| L2 Integration | 次点 | モジュール結合・DB アクセス・ミドルウェアチェーン | local で起動した実 DB。外部マネージドサービスは Stub |
| L3 External Integration | 少数 | コンポーネントと実外部サービスの結合点 | 実外部サービス（業務フローは縦断しない） |
| L4 E2E smoke | 最少 | クリティカルなユーザーフローの実 stack 縦断 | 実依存すべて（モックしない） |

**判断基準:**

- ロジック分岐・計算・バリデーション → L1 で検証する
- 結合点にバグが潜む箇所（Repository と DB の接続等） → L2（実 DB）で検証する
- 実外部サービスとの結合点 → L3 で検証する
- ユーザーの最重要パス → 実 stack を縦断する重要フローのみ L4 で検証する

## テストケースのカテゴリ観点

各ユーザーストーリーの AC から、以下の 4 観点でテストケースを導出する。観点ごとに「AC に対応するケースがあるか」を確認し、AC に根拠のないケースは追加しない。

| 観点 | 検証内容 | 例 |
|------|---------|-----|
| 正常系 | 期待入力で期待結果が返る | 有効な入力でリソースが作成される |
| 異常系 | 不正入力・依存障害で定義されたエラーが返る | 必須項目欠落で 400、依存先障害で定義済みエラー |
| 境界値 | 値域・件数・長さの境界での振る舞い | 上限ちょうど / 上限 +1、空リスト、最大長文字列 |
| 権限 | 認可されない主体が操作できない | 権限のないロールでのアクセスが拒否される |

## 設計原則

### 1. State over Interactions — 結果を検証する

振る舞いの**結果（状態変化・戻り値）**を検証する。メソッドが何回呼ばれたかは検証しない。

```typescript
// Good: 結果を検証
const result = await service.transition(id, Status.InTransit);
expect(result.status).toBe(Status.InTransit);

// Bad: 内部呼び出しを検証（実装の詳細に依存）
expect(repository.update).toHaveBeenCalledWith(id, { status: "IN_TRANSIT" });
```

**なぜ:** 内部呼び出しの検証はリファクタリング耐性がない。実装を変えるたびにテストが壊れる。

### 2. DAMP over DRY — テストは可読性を優先する

テストコードでは重複排除（DRY）より、わかりやすい重複（DAMP: Descriptive And Meaningful Phrases）を優先する。
失敗時に前提・操作・期待値がその場で読めない共有ヘルパー（`doTransition(...)` + `assertSuccess(...)` のような抽象）は作らない。

**DRY にしてよいもの:** テストデータ生成（`createTest*` ファクトリ）とセットアップヘルパーは共通化してよい。抽象化してよいのは**データ生成**であり、**アサーション**ではない。

### 3. Arrange-Act-Assert

全テストを 3 段構成で書く。セクション間に空行を入れて視覚的に分離する。

```typescript
it("有効な入力でレコードを作成できる", async () => {
  // Arrange
  const input = createTestInput({ owner: "alice" });

  // Act
  const result = await service.create(input);

  // Assert
  expect(result.id).toBeDefined();
  expect(result.owner).toBe("alice");
});
```

### 4. 1 テスト 1 概念

1 つのテストケースでは 1 つの振る舞いだけを検証する。正常遷移・異常遷移・履歴検証を 1 テストに詰め込まない。
複数概念を混ぜると、最初のアサーション失敗で後続が実行されず原因特定が遅れる。

## テストダブル方針

| 優先度 | 種別 | 説明 | 使いどころ |
|--------|------|------|-----------|
| 1 | **Real** | 実際の依存をそのまま使う | local 起動した実 DB・実サービス。**default** |
| 禁止 | ~~Fake~~ | 簡易実装で振る舞いを再現（InMemory 実装等） | **新規作成禁止**。Real が動かないなら Real が動くよう設計を見直す |
| 2 | **Stub** | 振る舞いを持たない型 fixture を返す | 接続情報・env オブジェクト等の型シェイプ |
| 3 | **Mock** | 呼び出し記録・関数差し替え | 副作用の発火確認、時刻・乱数の固定 |

**原則:**

- Real を default とする。Repository / Service / Provider 等の振る舞いを持つ依存は Real で検証する
- Fake は新規作成禁止。Real がテスト環境で動かない場合は、依存を local 起動可能なものに置き換えるか、標準 API ベースの実装に切り替えて Real が動くようにする
- 依存はコンストラクタ / 引数で注入する（DI）。モジュール丸ごとのモック差し替えは使わない
- Stub は「Real が要求する型を満たすだけ」の最小 object。分岐・状態保持・副作用を 1 行でも書いたら Fake になり禁止対象
- Mock が正当なのは次の 3 用途のみ:
  1. **副作用の発火確認** — 戻り値・状態で観測できない副作用（ログ出力・外部呼び出しの発火）
  2. **時刻・乱数の固定** — 非決定性の排除（フレーキーテスト防止として常に正当）
  3. **callback 経路の駆動** — DI 経由で渡す関数の制御
- 時刻・乱数・タイマーを内部で使うコードは、それらを上層から注入できる設計にすると Mock 自体が不要になり、より望ましい

## アンチパターン

### 1. トートロジカルテスト

実装ロジックをそのままテストの期待値にコピーする。テストが実装のオウム返しになり、仕様を検証していない。

```typescript
// Bad: 実装と同じ計算式を期待値に使う
expect(calculateFee(amount)).toBe((amount * FEE_RATE) / 100);

// Good: 仕様（AC）から導出した具体値で検証
expect(calculateFee(100)).toBe(3);
```

**防止策:** テストは AC（Given / When / Then）のみを根拠に書く。実装コードを見ながらテストを書かない。

### 2. 数合わせテスト

カバレッジや件数を上げるためだけの、ユーザーストーリーに対応しないテスト。getter の単純呼び出し、定数の再確認、フレームワークの動作確認などは第一原則違反として削除対象。

### 3. スナップショット乱用

大きなオブジェクトや出力を丸ごとスナップショットにすると、何を検証しているかが不明確になり、差分レビューで意味のある変更かノイズか判別できない。検証したいプロパティだけを明示的に assert する。
（例外: 型定義・スキーマの後方互換性チェックなど、全体構造の変化検知が目的の場合は許容）

### 4. テスト間の共有状態

テスト間でデータベースやグローバル変数を共有し、実行順序に依存する。各テストが独立したセットアップを持ち、任意の順序・単独で実行できること。DB を使うテストは `beforeEach` で初期化する。

### 5. 過剰モック

依存の大半をモックした結果、テストが「モック同士の会話」になり、実際の振る舞いを何も検証していない。
テスト対象が触れる依存の半数以上をモックしている場合、Integration テストに格上げするか、テスト対象の設計（依存過多）を見直す。

### 6. フレーキーテスト

非決定的な要素（時刻、乱数、ネットワーク、並行処理のタイミング）に依存し、ランダムに失敗する。

- 時刻 → fake timer で固定する
- 乱数 → シード固定またはスタブ化
- ネットワーク → local 起動の実サービスまたは境界 Stub に置き換える
- 非同期タイミング → リトライではなくイベント駆動のアサーションを使う

## レビューチェックリスト

テストを含む PR のレビュー / テスト実装時に確認する:

- [ ] 各テストケースがユーザーストーリー / AC に対応しているか（対応しない冗長・数合わせテストがないか）
- [ ] 正常系 / 異常系 / 境界値 / 権限の 4 観点が AC の範囲で揃っているか
- [ ] テスト名が「振る舞い + 期待結果」を表しているか（State over Interactions）
- [ ] 振る舞いを持つ依存（Repository / Service）を Mock / Fake で差し替えていないか（Real で検証する）
- [ ] モジュール丸ごとのモック差し替えをしていないか（DI 経由を優先）
- [ ] 「実装ロジックをコピーした期待値」になっていないか（トートロジカルテスト回避）
- [ ] スナップショットで巨大な構造を丸ごと固定していないか
- [ ] テストがデータ独立で、任意の順序・単独で実行できるか
