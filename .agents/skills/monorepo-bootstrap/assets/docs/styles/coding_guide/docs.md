# ドキュメント編集規約

> この文書は docs 編集時に守る「現状の事実のみ」原則と「実装整合の原則」の正本（SSOT）である。4 層モデル・3 原則・シグナル語 lexicon・実装整合の原則（アンカー付き主張と矛盾の 3 分類）・退避先判定を定義する。
> `/docs-sync` と `/code-sync` は本ガイドを検出基準の正本として参照する（各 skill の操作仕様は `docs/harness/skills/docs-sync.md` / `docs/harness/skills/code-sync.md` 側に、矛盾の検出から記録までの共通手順は `docs/harness/skills/shared/implementation-consistency.md` 側に書き、本書には書かない）。

## 適用範囲

「現状層の 3 原則」（後述）は以下のスコープに適用する。

| 対象（INCLUDE）                                                                              | 規約                                |
| -------------------------------------------------------------------------------------------- | ----------------------------------- |
| `docs/product/**/*.md`（ARCHITECTURE / TECH_STACK / TERMS / TEST_STRATEGY 等）               | 本ガイドの「現状層の 3 原則」を適用 |
| `docs/styles/**/*.md`                                                                        | 同上                                |
| `docs/harness/*.md`（直下のみ。`skills/` 配下は除外）                                        | 同上                                |
| ルート直下の `*.md`（`README.md` を除く。`CLAUDE.md` / `AGENTS.md` / `DEVELOPMENT.md` など） | 同上                                |
| `.claude/rules/*.md`                                                                         | 同上                                |

per-file 鮮度検証（実コード・設定との突合）の対象ファイルは `.claude/skills/docs-sync/references/freshness-policy.md`（プロジェクト profile）で定義する。TERMS.md の「初出」列の扱いは後述の例外規定に従う。

## 層の分離（4 層モデル）

ドキュメントは責務ごとに 4 層に分かれる。各層には書いて良いことと書いてはいけないことがある。

| 層                          | 配置先                     | 書いて良いこと                                               | 書いてはいけないこと                                       |
| --------------------------- | -------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| **現状層**（State-of-Now）  | 上表 INCLUDE のパス        | 今のシステム構成・採用技術・用語の現在値・ハーネス overview  | 経緯・移行履歴・代替案・撤回理由                           |
| **決定層**（Why）           | `docs/adr/`                | なぜその選択をしたか、代替案、撤回・置換の経緯               | 実装手順の詳細                                             |
| **調査層**（Investigation） | `docs/notes/research/`     | 候補比較、調査結果、提案案                                   | 採用確定の宣言（確定は ADR 経由）                          |
| **実装記録層**              | PR 本文・commit メッセージ | Issue ごとの計画・方針と却下案・スコープ外・検証結果・リスク | 横断的な現状記述（現状層へ）、恒久的な設計判断（決定層へ） |

### 現状層の責務

- 「今この瞬間にシステムはこうなっている」だけを書く
- 採用された技術スタック、稼働しているコンポーネント、使われている用語
- バージョン番号は **現行値** のみ（過去のバージョンは ADR 側）

### 決定層の責務

- 「なぜそれを選んだか」「他に何を検討したか」「いつ撤回したか」を書く
- Status: Proposed / Accepted / Deprecated / Superseded で時系列を表現
- 詳細運用 → `docs/adr/README.md`

## 現状層の 3 原則

現状層に書いてよい記述は、以下の 3 原則を満たすもののみ。

### 原則 1: No-Time（時間語禁止）

過去・将来・移行に関する語彙を本文中に置かない。読者が「いつ」を意識しなくても全体像が掴める状態を保つ。

| 禁止           | 例                                                                |
| -------------- | ----------------------------------------------------------------- |
| 過去形・経緯   | 「以前は X だったが、Y に変更した」「かつて X を使っていた」      |
| 撤回・廃止     | 「X は廃止された」「deprecated になった」「migrated from X to Y」 |
| 時系列マーカー | 「Q1 で移行済み」「before:」「after:」                            |
| 移行手順       | 「現状の X を Y に置き換える」                                    |
| 将来予定       | 「次回 X を廃止予定」「今後 Y にする」                            |

例外は「例外規定」の 3・4 に従う。

### 原則 2: No-Ticket-In-Prose（Issue / PR 番号を本文に埋め込まない）

`(#123)`、`Issue #123`、`PR #456` のような Ticket 参照を散文中に置かない。
読者が現状を理解するのに Ticket を辿る必要がないようにする。

| OK                                    | NG                                          |
| ------------------------------------- | ------------------------------------------- |
| ADR への末尾脚注リンク                | 文中に直接 `(Issue #123)` と書く            |
| 「詳細: `docs/runbooks/` の該当手順」 | 「ADR で確定した Pattern A（実施済み）」    |
| 表の備考列に ADR 参照を 1 個だけ置く  | 「これは #123 で追加された」「#456 で対応」 |

例外は「例外規定」の 2 に従う。

### 原則 3: No-Counterfactual（不採用・否定形禁止）

「X は採用しない」「Y ではなく Z」「代わりに W を使う」など、選択肢の否定・対比表現を書かない。
こうした記述は決定の経緯であり、決定層（ADR）に置く。

| 禁止                      | 代わりに書くべき内容    |
| ------------------------- | ----------------------- |
| 「ライブラリ A は不採用」 | 「ライブラリ B を採用」 |
| 「A ではなく B」          | 「B を採用」            |
| 「A は使用しない」        | 「B を採用」            |

例外は「例外規定」の 5 に従う。

## シグナル語 lexicon（regex 検出パターン）

`/docs-sync` / `/code-sync` が違反検出に使う正規表現の候補。本表が SSOT であり、skill 側は本表をそのまま参照する。

| カテゴリ       | 検出語（regex 風）                                                                                                                                                              | 違反の種類                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 時系列・経緯   | `移行(?:済み\|前\|後\|計画)\|以前は\|かつて\|廃止\|deprecated\|migrated from\|migrated to\|before:\|after:\|旧\|実施済み\|削除済み\|追加された\|変更された\|置き換え(?:た\|る)` | 原則 1 違反                              |
| 将来形         | `予定\|今後\|次回\|将来的に\|計画中`                                                                                                                                            | 原則 1 違反（将来計画は ADR / Issue 側） |
| 現状マーカー   | `現状（#\d+[^）]*）\|now:\|was:\|今は\|当面は`                                                                                                                                  | 原則 1 違反（暗黙の時系列）              |
| 裸 Ticket 参照 | `\(#\d+\)\|Issue #\d+\|PR #\d+`（リンク化されていない、本文中）                                                                                                                 | 原則 2 違反                              |
| 比較・否定     | `不採用\|代わりに\|ではなく\|は使用しない\|は使わない\|オーバースペック`                                                                                                        | 原則 3 違反                              |

> **注**: 上記の regex は概念的なパターンであり、skill 実装時は Read + 自然言語判断で文脈と
> 例外規定（次節）を照合する。機械的な grep だけでは例示コード内の「代わりに」のような
> 偽陽性を回避できないため、検出 → 文脈判定の 2 段構えで運用する。

## 例外規定（保持して良いもの）

以下は signal lexicon に該当しても削除しない。

1. **TERMS.md の「初出」列の要件 ID**: `BR-XXXX` / `IF-XXXX` / `DATA-XXXX` / `FR-XXXX` / `NFR-XXXX` / `SEC-XXXX`（`-FIX` 改訂サフィックス含む）は仕様参照であり、用語定義の根拠を示すための必須情報
2. **ADR / research / requirements / runbook への参照リンク**（脚注・末尾節・備考列）、末尾の「関連 ADR / 関連 Issue」節での Ticket 参照、段落全体が「外部接続先・出典」として機能する箇所（脚注・参考文献節）: 決定や調査の出典は決定層に書くが、現状層から正本へのリンクを張るのは許容
3. **現行値としてのバージョン番号**（node 22、TypeScript 5 系 等）: 採用ツール・ライブラリの semver 表記は時間語ではなく現在の値であり、経緯ではない
4. **中核ドキュメント先頭のメタフロント**: `> 決定日: YYYY-MM-DD` のような単一行メタは、決定の発効日を示すもので、中身は現状記述のため許容
5. **アーキテクチャ的不変条件**（「本システムは利用者の credential を保持しない」等）: 過去比較ではなく現在の構造的事実であり、記述してよい
6. **コード例・サンプル中の語彙**: 例示コード内で regex に該当してもコードであれば対象外

## 実装整合の原則

3 原則が「どう書くか」（形式）を定めるのに対し、本節は「書いた内容が実装と一致しているか」（内容）を定める。両者は直交する。3 原則を満たす記述でも、実装と食い違っていれば本原則の違反になる。

> **原則**: 記述が実装側の実体を名指しして述べる主張は、`origin/main` の実装と一致していなければならない。

### アンカー付き主張

本原則が対象にするのは「アンカー付き主張」である。実装側の実体（パス / リソース名 / 識別子 / エンドポイント / 設定キー / 数値パラメータ / 状態名 / 実行コマンド）を名指ししているため、実装を読めば真偽が判定できる記述を指す。

目的・背景・設計意図の説明のように、実装側の実体を名指ししない散文は対象外とする。真偽を機械的に決められず、書き換えが推測になるためである。

### 実装整合の適用範囲

3 原則の INCLUDE / 除外パスとは別のスコープであり、実装の挙動を説明する記述とソースコメントに適用する。走査対象の実体は各 skill 正本が持ち、本書には列挙を複製しない。

| 記述の種類                       | 走査対象の正本                       |
| -------------------------------- | ------------------------------------ |
| Markdown（現状層 docs・runbook） | `docs/harness/skills/docs-sync.md`   |
| ソースコメント                   | `docs/harness/skills/code-sync.md`   |
| README                           | `docs/harness/skills/readme-sync.md` |

ソースコメントへの適用では、アンカーを同一ファイル内の実装から優先して引き当てる。`TODO:` / `FIXME:` / `NOTE:` / `HACK:` マーカー付きのコメントは経緯・将来メモの性格を持つため対象外とする。

### 矛盾の分類

矛盾を見つけたとき、記述側を直してよいとは限らない。記述が規範（要件など）で実装がそれを満たしていない場合、記述を実装に合わせて書き換えると、仕様違反が記録ごと消える。そのため矛盾は次の 3 分類のいずれかに割り当てる。

| 分類     | 意味                                             | 扱い                                                                               |
| -------- | ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 記述修正 | 実装が正で、記述が実装に追随できていない         | 記述側を実装に合わせて修正する                                                     |
| 実装疑い | 記述が規範で、実装がそれを満たしていない         | 記述を書き換えない。根拠を添えて記録する                                           |
| 判定不能 | 記述の層だけでは、どちらを正とするかが決まらない | 記述を書き換えない。下記の決め方で正とする側を決め、決めた側と理由を添えて記録する |

文書を編集するのは「記述修正」だけである。「実装疑い」と「判定不能」は規範層の記述を保全するため、根拠（実装側のパスと識別子、記述側の該当箇所）を PR 本文に記録して実装側の判断に渡す。実装が正とは限らないため、矛盾は分類を経てから扱う。記録の形式と検出の手順は `docs/harness/skills/shared/implementation-consistency.md` が定める。

分類は記述が属する層で既定を決め、内容で覆す。

| 層     | 該当する記述                                                    | 既定の分類                                     |
| ------ | --------------------------------------------------------------- | ---------------------------------------------- |
| 記述層 | 現状層 docs・runbook・README・ソースコメント                    | 記述修正                                       |
| 規範層 | `docs/requirements/**`・`docs/customer/**`（opt-in 区画採用時） | 実装疑い、または判定不能（記述を書き換えない） |

記述層であっても、実装側が要件の観点で誤っているように見える場合は「判定不能」とする。ADR の決定事項は決定層であり、既定の割当に含めない。

「判定不能」は [single-solution](../team-feedback/single-solution.md) の 3 条件で正とする側を 1 つに決める。規範層の記述が相手のときは、記述を仕様とみなして実装を記述に合わせる案を既定にする。人間の追加承認は要らない（人間は PR のレビューで覆せる）。

### 修正の作法

「記述修正」を行うときは次に従う。

- 修正は主張そのものの置換に閉じる（値・識別子・状態名の置換、主張 1 文の書き換え）。節の再構成や手順の増減は行わない
- 修正には実装側の根拠（パスと識別子）を添える。根拠を示せない不一致は修正せず、判定不能として記録する
- 修正後の文面も 3 原則を満たす（「30 分間隔に変更された」と書かず「30 分間隔」と書く）

## 退避先の判定基準

違反を見つけたとき（人間レビュアが手動で削除する場合も、`/docs-sync` が処理する場合も）、
該当事実をどの層へ退避すべきかを以下の表で判定する。

| 違反の種類                 | 推奨退避先                            | 例                                              |
| -------------------------- | ------------------------------------- | ----------------------------------------------- |
| 技術選定の理由・代替案     | ADR（`docs/adr/`）                    | 「ライブラリ A 不採用」→ ADR の「比較・選定」節 |
| 過去のバージョン・移行履歴 | ADR（Superseded 経由）                | 「X から Y に移行」の経緯                       |
| 候補比較・調査結果         | research（`docs/notes/research/`）    | ツール比較の調査結果                            |
| 仕様の経緯                 | requirements の `-FIX` 改訂または ADR | エンドポイントのリネーム経緯                    |
| 設定変更の手順             | runbook（`docs/runbooks/`）           | 環境リセット手順                                |

退避先に該当事実が既に書かれていれば現状層から削除（または末尾脚注リンクへ置換）してよい。
書かれていなければ、退避先を先に起票する。

## 書き手向けクイックチェック

現状層ドキュメントを編集するときに毎回確認するチェックリスト。

- [ ] 書こうとしている記述は「今こうなっている」事実か？（過去・将来・移行の話なら ADR 側）
- [ ] 文中に Issue / PR 番号を埋め込んでいないか？（埋め込むなら末尾「関連リソース」節へ）
- [ ] 「X は不採用」「Y ではなく Z」と書いていないか？（書くなら ADR 側、現状層には Z の採用事実だけ）
- [ ] 「migrated from」「以前は」「廃止」「deprecated」等の時系列語を使っていないか？
- [ ] バージョン番号を書く場合、現行値だけになっているか？（過去版は ADR 側）
- [ ] 削除した内容について、退避先（ADR / research / requirements / runbook）の有無を確認したか？
- [ ] 実装の実体（パス・リソース名・識別子・数値パラメータ・コマンド）を名指しした箇所は、`origin/main` の実装と一致しているか？一致しない場合、記述が規範でないことを確認してから直したか？

## 違反例とリファクタ例

### 違反例 1: 経緯記述（原則 1 違反）

```markdown
# BAD

- **Deploy CI**: `.github/workflows/ci.yml` が一手に担当（旧 deploy workflow は移行で削除済み）。
```

```markdown
# GOOD

- **Deploy CI**: `.github/workflows/ci.yml` が一手に担当（format:check → test → build を実行）。
```

→ 「旧 deploy workflow は移行で削除済み」は経緯（原則 1 違反）。ADR に統合経緯が記録されていれば削除。なければ ADR 起票要。

### 違反例 2: 比較記述（原則 3 違反）

```markdown
# BAD

| 4 | API Server | フレームワーク B | フレームワーク A は型安全性が弱く設計が古い |
```

```markdown
# GOOD

| 4 | API Server | フレームワーク B | スキーマ定義から API 仕様と SDK を単一定義で導出できる |
```

→ 「フレームワーク A は…」は不採用理由（原則 3 違反）。詳細比較は ADR / research 側に記録して現状層から削除する。

### 違反例 3: 将来形（原則 1 違反）

```markdown
# BAD

- **release ブランチ → prod 環境（push で apply）**: リリース後に有効化予定
```

```markdown
# GOOD（prod 整備前の段階の場合）

- **release ブランチ**: prod デプロイ用ブランチ
```

→ 「有効化予定」は将来形（原則 1 違反）。予定は ADR / Issue 側で管理。

### 違反例 4: 実装との不一致（実装整合の原則違反）

```markdown
# BAD

- **再処理ジョブ**: 失敗したジョブを 20 分間隔で再処理する。
```

```yaml
# 実装（ジョブ定義）
schedule: "0 * * * *" # 毎時 1 回
```

```markdown
# GOOD（記述層の記述なので「記述修正」）

- **再処理ジョブ**: 失敗したジョブを毎時 1 回再処理する（`schedule: "0 * * * *"`）。
```

→ 数値パラメータ（間隔）を名指しした記述が実装と食い違っている。記述が現状層 docs なら「記述修正」として実装に合わせ、根拠（ジョブ定義のパスと `schedule` キー）を PR 本文に添える。同じ記述が要件正本（規範層）にある場合は編集せず、「実装疑い」として根拠付きで PR 本文に記録する。
