# テスト戦略 — {{PRODUCT_NAME}}

> この文書はテスト全体の地図（what / where）の正本である。どのテストレベルで・何を・CI のどのトリガーで検証し、網羅をどう測るかを定める。
> 個々のテストの書き方（how）は `docs/styles/coding_guide/testing_principles.md` が正本であり、本書では繰り返さない。

## テストレベル定義

機能テストは **スコープ（どこまで結合して検証するか）** でレベルを分け、**上から順に当てはめて**判定する。下にいくほど実行コストが高く、外部依存も増える。迷ったら「テスト対象が実 I/O（実 DB・実外部サービス）に触れるか」で判定する。

| レベル | 判定基準（この順に当てはめる） | 検証対象の例 | 外部依存の扱い | CI 実行 |
|--------|------------------------------|------------|--------------|---------|
| **L1 Unit** | 実 I/O に触れない純粋ロジック | （bootstrap 時に具体化） | なし（時刻 / 乱数のみ Mock） | 全 PR |
| **L2 Integration** | 実 DB（testcontainers 等）に触れる。外部マネージドサービスは Stub / Mock | | 実 DB のみ | 全 PR（コード変更時） |
| **L3 External Integration** | 実外部マネージドサービスとの **結合点** を検証。業務フローは縦断しない | | 実外部サービス（dev 環境） | bootstrap 時に具体化 |
| **L4 E2E smoke** | 複数の実依存をまたぐ **業務フロー全体** を端から端まで縦断 | | 実 stack 全体 | bootstrap 時に具体化 |

> CI 実行列は bootstrap 時に具体化する。既定 workflow は `.github/workflows/ci.yml` のみで、定期実行 workflow は持たない。定期実行を追加する場合は `docs/harness/scheduled-operations.md` の設計ガイドに従う。

> レベルの境界はファイル名でなく「実 I/O に触れるか」で判定する。L3 は「1 コンポーネント × 1 外部サービスの結合点」、L4 は「業務ユースケースが全 stack を縦断するか」を見るもので、失敗の意味が異なるため統合しない。

## 網羅基準

**第一原則（テスト規約の正準文）**:

> テストは「ユーザーストーリーの設計」→「それに対応するテストのみを作成」の順で書く。ユーザーストーリーに対応しない冗長なテスト、数合わせのテスト、実装詳細に密結合してすぐ形骸化するテストは書かない。

これを踏まえ、網羅は次の方針で測る。

- 網羅は **「要件から導出したユーザーストーリー（US）/ 受入条件（AC）のうち、テストで担保された割合」** で測る（spec ベース）。
- 行・分岐などのコード実行カバレッジは **主要指標にしない**。カバレッジの高さはバグ検出力と一致せず、カバレッジ稼ぎ目的の「実装をそのまま期待値に写しただけのトートロジカルテスト」を誘発するため。
- テストは AC のみを根拠に先に書き（Red → Green）、実装を見ながら期待値を写さない。
