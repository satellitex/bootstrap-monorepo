## 判定の原則

版は `MAJOR.MINOR.PATCH` の 3 桁で表す。

| 桁    | 上げる変更                                           |
| ----- | ---------------------------------------------------- |
| MAJOR | 既存の利用者に影響する、互換性の無い変更             |
| MINOR | 互換性を保った機能追加・拡張                         |
| PATCH | 既存の仕様を変えない、不具合・脆弱性・内部処理の修正 |

1. 最上位の問いは「既存の利用者・システムが、変更後も修正なしで使えるか」とする。使えない可能性がある変更は MAJOR 側で判定する。
2. 互換性は、外部から観測できる契約（入力の受理範囲・応答の内容とステータス・認証と接続の方式）で判定する。DB や基盤の変更で従来の使い方が失われれば MAJOR、公開仕様を保った内部修正なら PATCH とする。
3. 判定が割れる場合の優先順位は、後方互換性なし → MAJOR、互換だが機能追加 → MINOR、既存仕様の不具合修正 → PATCH とする。
4. 不具合の修正であっても、それまで成功していた呼び出しの結果（ステータス・項目の集合・意味）が変わる場合は、非互換の区分で判定し、PATCH より優先する。
5. どの区分にも該当しない変更は、変更前と同じ呼び出しが同じ結果を得られるかで判定する。判断が付かないものは非互換の疑いとして採番を保留し、保留の理由を Issue / PR に記録する。
6. 非互換の変更は、影響範囲の小ささや採番の窓の都合にかかわらず MAJOR で出す。
7. 採番済みの版の内容は変更しない。修正は新しい版として出す。

## 互換性の区分（HTTP API）

### 非互換（MAJOR）

| 領域             | 変更                                                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 操作             | 操作の削除、動作仕様の変更                                                                                                         |
| リクエスト       | 必須項目の追加、任意項目の必須化、受理範囲の縮小、型の変更、項目名の変更、結果に影響していた項目の削除、列挙値の削除、既定値の変更 |
| レスポンス       | 項目の削除・名称変更・型変更・null 許容化・意味の変更、列挙値の削除、既定のソート順やページングの変更                              |
| エラー           | 既存の条件で返すステータスの変更、エラー識別子の削除・名称変更                                                                     |
| 非同期・冪等     | 終端状態の集合の変更、冪等キーの解釈の変更                                                                                         |
| 認証・認可・流量 | 認証方式の変更、設定済みの値の失効、必要権限の追加、権限の対応づけの縮小、制限値の引き下げ                                         |

### 互換（MINOR）

- 新規の操作、任意項目の追加、応答への項目の追加、要求側の列挙値の追加
- バリデーションの緩和、非終端の中間状態の追加
- 非推奨印の付与（機能の実体を残すもの）
- 新しい認証方式の追加、大幅な性能改善
- 結果に影響しないリクエスト項目の削除。従来の入力を引き続き受理できることを確かめる。未知の項目を拒否する設定の場合は、任意項目として残し、非推奨印を付ける

### 修正（PATCH）

- 不具合・エラー処理・ログ・脆弱性の修正
- 外部仕様を変えない内部処理の修正
- 提供する契約仕様書に含める説明文・例・誤記の修正

### 列挙値の扱い

レスポンスの列挙値の追加は非互換として扱う。値集合が拡張されることと、未知の値を無視することを契約に明記した列挙に限り、追加を互換とする。この既定は project の判断で変更できる。

### セキュリティ修正の桁

| 修正の内容                                                                       | 桁    |
| -------------------------------------------------------------------------------- | ----- |
| 既存の利用方法を変えない脆弱性の修正                                             | PATCH |
| 新しい認証方式の追加など、利用者が任意に採用できる対策の追加                     | MINOR |
| 既存の認証方式の提供終了、受理していた入力の拒否など、既存の利用方法を変える対策 | MAJOR |

### 契約仕様書の差分に現れない互換性要因

入力の正規化、非同期処理の終端状態、既定の並び順、必要権限、流量制限は、契約仕様書の差分に現れないことがある。変更前後の実装と設定から同じ利用方法で得られる結果を確かめ、判定の根拠を Issue / PR に記録する。

## 採番の実施

1. 対象ブランチで現在の版番号の値を最後に変えたコミットを特定し、前後の差分で値の変更を確かめる。そのコミットの直後から判定時点の先端までの全変更を調べる。`pr-auto-merge` から実行する場合は、その回のマージ処理が終わった時点を使う。マージが 0 件でも、人が先に取り込んだ変更があり得るため判定する。
2. 区間の両端で公開契約と稼働する実装・設定・本番依存を比較する。採番対象の変更があれば、その中で最も大きい桁を 1 回だけ上げる。例えば、互換性を保った操作の追加と内部修正を一緒に出すときは MINOR を 1 回上げる。
3. 次の表に従って結果を記録する。起点を進めるのは採番が対象ブランチに反映されたときとする。採番 PR が開いている間に対象の差分が変わった場合は、最新の区間で再判定する。

| 判定結果 | 扱い |
| -------- | ---- |
| 対象の変更が 0 件 | 版と起点を維持する。配布物があれば、その成果物の判定に進む。 |
| PATCH / MINOR | 版の正本を更新する採番 PR を作り、通常の PR と同じ検査・マージ条件を適用する。MINOR は利用者向けの変更履歴も同じ PR で更新する。 |
| MAJOR または非互換の疑い | 区間全体の採番を保留する。該当箇所、影響を受ける利用方法、判断が必要な点を Issue / PR に記録する。MAJOR は責任者の明示的な指示と移行方法の合意を受けて採番する。 |
| 起点や比較材料を確認できない | 「材料不足」と記録し、足りない資料を明示する。区間と差分を検証できるまで採番を見送る。 |

本番反映の前に、反映予定の稼働内容が採番済みの版に含まれることを確かめる。採番を保留・見送りとした変更や、採番 PR が未マージの変更は、次の判定に引き継ぐ。開発ブランチへの自動マージを許可している場合も、本番反映にはこの確認を適用する。

## SDK（配布パッケージ）の桁

各パッケージについて、利用者が取得できる直近の公開版と、今回配布するビルド成果物を比較する。公開する関数・型・設定と、対応する実行環境を確認し、パッケージごとに桁を決める。通常は配布物に差分がなければその版を維持する。公開契約の MAJOR に追従して同時提供する取り決めがある SDK は、契約の移行と同じリリースで SDK の MAJOR も上げる。

| 桁    | 上げる変更                       |
| ----- | -------------------------------- |
| MAJOR | 公開名の削除・改名、必須項目の追加、対応する実行環境の縮小など、利用側の修正が必要な変更 |
| MINOR | 公開する関数・型・任意項目などの、互換性を保った追加 |
| PATCH | 公開仕様を保った内部修正、依存更新、同梱する説明資料の修正 |

PATCH / MINOR の採番 PR には、配布物ごとの変更履歴を含める。MAJOR や互換性が未確定の配布物は自動採番を保留する。依存先の契約版を保留・見送りとした場合は、それに追従する配布物も保留する。逆に、配布物だけが保留となり、サービスを単独でリリースできる場合は、契約版の判定に従って本番反映を判断する。
