## 判定の原則

版は `MAJOR.MINOR.PATCH` の 3 桁で表す。

| 桁 | 上げる変更 |
|----|-----------|
| MAJOR | 既存の利用者に影響する、互換性の無い変更 |
| MINOR | 互換性を保った機能追加・拡張 |
| PATCH | 既存の仕様を変えない、不具合・脆弱性・内部処理の修正 |

1. 最上位の問いは「既存の利用者・システムが、変更後も修正なしで使えるか」とする。使えない可能性がある変更は MAJOR 側で判定する。
2. 互換性は、外部から観測できる契約（入力の受理範囲・応答の内容とステータス・認証と接続の方式）で判定する。DB 構造・アーキテクチャ・基盤ソフトウェアの変更は、外部から観測できる互換性を失わせる場合に限り MAJOR とし、失わせない場合は内部処理の修正として PATCH にする。内部変更のたびに公開する版が上がり続けることを避けるためである。
3. 判定が割れる場合の優先順位は、後方互換性なし → MAJOR、互換だが機能追加 → MINOR、既存仕様の不具合修正 → PATCH とする。
4. 不具合の修正であっても、それまで成功していた呼び出しの結果（ステータス・項目の集合・意味）が変わる場合は、非互換の区分で判定し、PATCH より優先する。
5. どの区分にも該当しない変更は、変更前と同じ呼び出しが同じ結果を得られるかで判定する。判断が付かないものは非互換の疑いとして採番を保留し、保留の理由を Issue / PR に記録する。
6. 非互換の変更は、影響範囲の小ささや採番の窓の都合にかかわらず MAJOR で出す。特例は置かない。
7. 採番済みの版の内容は変更しない。修正は新しい版として出す。

## 互換性の区分（HTTP API）

### 非互換（MAJOR）

| 領域 | 変更 |
|------|------|
| 操作 | 操作の削除、動作仕様の変更 |
| リクエスト | 必須項目の追加、任意項目の必須化、受理範囲の縮小、型の変更、項目名の変更、結果に影響していた項目の削除、列挙値の削除、既定値の変更 |
| レスポンス | 項目の削除・名称変更・型変更・null 許容化・意味の変更、列挙値の削除、既定のソート順やページングの変更 |
| エラー | 既存の条件で返すステータスの変更、エラー識別子の削除・名称変更 |
| 非同期・冪等 | 終端状態の集合の変更、冪等キーの解釈の変更 |
| 認証・認可・流量 | 認証方式の変更、設定済みの値の失効、必要権限の追加、権限の対応づけの縮小、制限値の引き下げ |

### 互換（MINOR）

- 新規の操作、任意項目の追加、応答への項目の追加、要求側の列挙値の追加
- バリデーションの緩和、非終端の中間状態の追加
- 非推奨印の付与（機能の実体を残すもの）
- 新しい認証方式の追加、大幅な性能改善
- 結果に影響しない項目の削除。未知の項目を拒否する設定の場合は、削除せず任意項目として残し、非推奨印を付ける

### 修正（PATCH）

- 不具合・エラー処理・ログ・脆弱性の修正
- 外部仕様を変えない内部処理の修正
- 説明文・例・誤記の修正

### 列挙値の扱い

レスポンスの列挙値の追加は非互換として扱う。値集合が拡張されることと、未知の値を無視することを契約に明記した列挙に限り、追加を互換とする。この既定は project の判断で変更できる。

### セキュリティ修正の桁

| 修正の内容 | 桁 |
|-----------|-----|
| 既存の利用方法を変えない脆弱性の修正 | PATCH |
| 新しい認証方式の追加など、利用者が任意に採用できる対策の追加 | MINOR |
| 既存の認証方式の提供終了、受理していた入力の拒否など、既存の利用方法を変える対策 | MAJOR |

### 差分に現れない互換性要因

正規化規則・非同期処理の終端状態・暗黙の並び順など、差分に現れない互換性要因は、設計時に人間が判定し、根拠を変更提案（Issue / PR）に記録する。

## SDK（配布パッケージ）の桁

| 桁 | 上げる変更 |
|----|-----------|
| MAJOR | 公開する口の、互換性の無い変更 |
| MINOR | 公開する口の、互換性を保った追加 |
| PATCH | 公開する口を変えない修正 |
