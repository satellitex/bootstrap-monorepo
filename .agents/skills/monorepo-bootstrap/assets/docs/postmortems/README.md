# インシデント記録（`docs/postmortems/`）

> この文書は `docs/postmortems/`（インシデントの作業記録と振り返りの置き場）の運用規約である。記録の様式は `docs/templates/` に置き、ここには書かない。
> 内部向け文書で、読者は運用担当者とエージェントである。

本ディレクトリに置くのは、インシデントに該当すると判定した事象に限る。判定の基準と判定する責任者は project が定める。

- 重要度の基準: TODO(記入方法: 重要度（高 / 中 / 低）の判定基準を決め、`docs/runbooks/` の手順書に置いて、ここからリンクする)
- 該当性を判定する責任者: TODO(記入方法: 判定する役割を決めて記入する)

該当しないと判定した一次調査の記録先は対応 Issue とし、記録のためだけのブランチや PR を作らない。記録のための PR はマージする担い手が決まらず残りやすいため、本ディレクトリには該当時の記録だけを置く。

判定は後から変わる。該当しないとした事象を、責任者が後に該当と判断した場合は、その時点で本ディレクトリに起こす。作業記録（`timeline.md`）が無ければ、振り返り（`postmortem.md`）だけを置いてよい。様式の判定者欄は記録欄であり、承認待ちで作業を止めない。

## 置くもの

| ファイル | 内容 | 様式 |
| --- | --- | --- |
| `<YYYY-MM-DD>_<slug>/timeline.md` | 対応中の観測・判断・実施を時刻付きで記録した作業ログ | `docs/templates/incident-timeline.md` |
| `<YYYY-MM-DD>_<slug>/postmortem.md` | 影響・タイムライン・検知の評価・根本原因・対処・アクションアイテムをまとめた、blameless な振り返り | `docs/templates/postmortem.md` |

様式をコピーして、人間またはエージェントが作成する。

## 命名

- ディレクトリ: `<YYYY-MM-DD>_<slug>`。日付は発生日（タイムゾーンは下記の統一値）、slug は検知元（アラート名・報告経路）に由来する英語 kebab-case（例: `2026-01-01_db-connection-saturation`）
- 同日に同じ検知元で複数回発生した場合は、slug の末尾に `-2` のように連番を付ける

## 書き方の規約

- 時刻はタイムゾーンを明記し、project で 1 つに統一する。TODO(記入方法: project の標準タイムゾーンを決めて記入する)
- 事実には情報源（監視ツールやログ照会へのリンク、PR、人間からの聞き取り）を添える。情報源が無いものは仮説と明記する。後から事実を再確認できるようにするため
- 原因は人ではなく仕組み（検知・手順・設計・コード）に求め、人は役割で書く（blameless）。個人の注意に帰すと再発を防ぐ仕組みの改善に結びつかない
- 秘匿値（接続文字列・API key・password・token・個人情報）は載せない
- 該当しない節は削除せず「なし」と明記する。記入漏れと区別するため
- 内部の識別子（Issue 番号・アカウント ID）を含んでよい。公開サイトを持つ場合は、公開区画へそのまま移さず、公開ポリシーの判定を経る

## 一覧

本ディレクトリは `INDEX.md` を持たない。ディレクトリ名が日付と対象を表すため、`ls` で一覧できる。件数が増えて索引が必要になったら、`INDEX.md` の新設と更新主体の割当を決める（割当表 → `docs/harness/skills/shared/index-writer-policy.md`）。
