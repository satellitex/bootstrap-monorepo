# runbooks 運用ガイド

> この文書は `docs/runbooks/`（セットアップ・運用手順書）の書き方の規約の正本である。手順書ごとに求める必須要素、成功判定と結果不明の書き方、状態を変える手順の確認観点、設定投入手順の値表を定める。
> 手順書の一覧は [`INDEX.md`](./INDEX.md)、分岐の根拠と例外系の設計判断は ADR（`docs/adr/`）に置く。

## 位置づけ

- 手順書は、読んだ人またはエージェントが実行でき、結果を見て次の操作を判断できる文書として書く。
- 本文は happy-path の手順を主とし、失敗・結果不明のときは分岐先（次の操作）を書く。
- 節構成は規定しない。規定するのは要素の欠落だけである。手順書ごとに適した構成を選べるようにし、必要な情報が抜けることを防ぐ。

## 手順単位の必須要素

副作用（状態変更・特権操作・不可逆な操作）のある手順は、次の 8 要素をすべて書く。読み取り専用の手順は、実施者・権限・成功判定の 3 要素を書く。

| 要素 | 書くこと |
| --- | --- |
| 実施者 | 実行者・承認者・依頼先。役割で書く |
| 権限 | 必要な role と credential の種別。値は書かない |
| 事前状態 | 開始条件と、開始してはならない状態（中止条件）。対象は環境・ブランチ・範囲で固定する |
| 実行 | コマンドや操作。秘密値・実データ・環境固有の値はプレースホルダにする |
| 成功判定 | 実行の成功と目的の成功を分けて書く（次節） |
| 次の操作 | 成功時・失敗時・結果不明時の分岐先 |
| 再実行可否 | 冪等性、再実行してよい条件、再実行してはならないケース |
| 証跡 | 記録する項目と保存先 |

## 成功判定と結果不明

実行基盤の表示（終了コード 0、応答 2xx、ジョブの緑表示）は、目的が達成されたことを意味しない。次のとおり書く。

1. 成功判定は 2 段で書く。実行の成功（終了コード 0 / 応答 2xx / ジョブ緑）に加えて、目的の成功（応答の業務フィールド、状態遷移、成果物の存在、読み戻し）を確認する。成功条件には目的の成功を使う。
2. サンプル出力の動的な値（ID・時刻・件数）との完全一致を成功条件にしない。実際の出力から取得し、次の手順へ渡す変数として書く。
3. 結果と次の操作は分岐表で書く（例: 入力エラーは入力を修正して再実行 / 権限エラーは権限を確認 / 競合は状態を確認 / 制限超過は待機 / タイムアウト・5xx・応答喪失は照会で突合）。HTTP 以外の手順では、終了コード・ジョブ状態・成果物に読み替える。
4. 結果不明（タイムアウト・5xx・応答喪失）は、成否を断定せず状態の照会で突合する。記録が見つからないことを、不成立の証拠にしない。自動再試行、別の冪等キーでの回避、時間待ちの反復を手順に足さない。二重実行を招く操作は、結果が確定するまで繰り返さない。
5. 突合に使う識別子（送信前に確定する識別子、相関 ID、実行 ID、冪等キー）は保持し、実際の出力で確認できるものだけを例に書く。出力されない識別子を創作しない。同名でも由来の異なる ID は区別して書く。
6. 再実行可否には、冪等キーの範囲、同一キーで再実行してよい条件、再実行してはならないケースを書く。

## 状態を変更・停止する手順

停止・縮退・一時的な保護の緩和・設定変更を含む手順で、本番や共有環境を変えるものは、次の観点を確認する。開発環境は壊れても復旧できる前提のため、確認は推奨にとどめる。コマンドの実行は復旧の完了を意味しないので、7 の確認まで手順に含める。

1. 対象指定: 環境・ブランチ・範囲を固定する
2. 排他の範囲: 止まる書き込み経路と、止まらない経路を書く
3. 変更前の状態をスナップショットとして証跡に保存する
4. 停止の完了確認: 新規の起動を止めることと、開始済みの処理・ロック・キュー内の処理が収束したことは別に確認する。停止や完了を確認できなければ開始しない
5. 結果の保全: 出力の保存が成功したことを、処理の成功とは別に確認する
6. 元の状態への復帰は、既定値や推測値ではなく、保存したスナップショットの値そのものへ戻す
7. 復帰後の状態確認と、復帰が完了するまでの保護（アクセス制御・メンテナンス状態）の維持。一時的に緩めた権限や保護は、使用のたびに戻し、戻ったことを確認する

## 設定投入型の手順（リポジトリ外のサービス設定）

スケジューラ・外部サービス・実行基盤など、リポジトリの外に実体がある設定の手順では、次を書く。エージェントはリポジトリ外の設定を直接検証できないため、期待値をリポジトリ内に残す。

- 期待値（起動指示の文面、値表）はリポジトリ内の手順書を正本とし、実体側は写しとして扱う
- 値表は「項目 / 値 / 理由」の列で書く。設定漏れで実害が出る項目には、「確認方法」（設定が効いていることの確かめ方）と「未設定時の症状」（その設定が無いとどう失敗するか）も書く
- 初回は、書き込みを伴わない試行（dry-run や読み取り専用の確認）で効いていることを確かめてから、書き込みを伴う設定を有効にする。有効化後の最初の実行では、書き込み系の操作が実行環境に止められていないかを実行記録で確認する
- 秘密値は名前と投入手順だけを書き、値は書かない。投入は人間の明示承認が必要な操作である
- 実行基盤のステータス（緑表示）は目的の成功を意味しない。結果を読む場所を併記する

## 実施記録（推奨様式）

副作用のある手順の実施記録は、次の項目を最小とする。

- 実行主体 / 実行時刻（タイムゾーンを明記）/ 対象 / 操作種別 / 理由または相関 ID / 結果

作業の都度記録し、終了後に記憶から復元しない。訂正は元の記録を残して追記する。秘密値、原本の内容、クエリの全文は記録しない。

## 分割・統合・移動

手順書を分割・統合・移動するときは、実行例・事前状態・中止条件・再実行条件・成功判定・証跡を一緒に移す。責任の所在（実施者・承認者）の変更は、文書の分割や移動に含めず、別の変更として扱う。
